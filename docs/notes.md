# 工作笔记

> 记录人：我 ｜ 起始：2026-09-22
> 用途：把「过程」变成可以讲出来的东西。面试素材从这里长出来。
> 配套：`docs/workflow.md`（流程与理由）、`CLAUDE.md`（硬约束）

## 写入规则

| 方式 | 谁写 | 什么时候 |
|---|---|---|
| **手动** | 我 | 任何时候。想法、疑问、决定、情绪、卡住的地方，都行 |
| **自动** | Claude | ① 每个阶段收尾时 ② 出现「AI 添乱」时**当场**记 ③ 我说「记一下」时 |

第 ② 条是刻意的：**添乱要当场记**。事后回忆会自动美化，而「AI 在哪里添乱」恰恰是最难拿到、也最值钱的部分。

## 条目格式

```
### YYYY-MM-DD · 阶段或事件

- **AI 做了什么** ——
- **哪里帮上忙** ——
- **哪里添乱** ——
- **我的判断** ——
```

四行里只有第一行 = 流水账。**第四行才是关键。**

**唯一的硬规矩**：第四行由我说。Claude 可以提示「这里你做了判断」，但不得代写。写不出来就留空。

### 2026-10-06 · 判断补记：RAG 在本业务里是「有需求、可行、合适」的

- **背景** —— 切片 2 验收闭环后，用户主动追问「我这个业务情形下，用 RAG 做问答是否合逻辑、是否有需求」。这是对 10-01「入口选错」教训的一次主动回看，结论由 AI 结构化、用户确认：
- **结论（用户口述确认）** —— **使用 RAG 存在业务需求，业务上可行且合适**——但仅对症状描述入口（入口②）成立；检测结果入口（入口①）是精确 key 查表，明确不该用 RAG（D12）。双入口的划分本身就是这个判断的答案。
- **入口② 合逻辑的三个条件（缺一不可）** ——
  1. **查询没有精确 key**：农户说「叶子卷起来发白」，说不出「稻纵卷叶螟」——自由文本对结构化语料，SQL 与关键词检索都过不了口语-术语的语义鸿沟
  2. **答案必须可信且可溯源**：喷错药有真实农损；裸 LLM 不掌握 102 虫的本地防治方案只能编——RAG 的本质是给生成侧上证据约束（检索不可信即拒答，fail-closed 的业务根基）
  3. **语料太小不适合微调**：306 块语料微调成本高、过拟合、更新语料要重训；RAG 换语料只需一条命令重建索引（几秒）。知识规模小、更新频率高、结构化好 → RAG；反之才考虑微调
- **主动让步（面试硬点）** —— 306 块的规模，纯 BM25 也能做一部分，RAG 不是唯一解。赢在两点：BGE embedding 的**语义对称性**（「发白」↔「白色条斑」）；相似度分数有稳定 [0,1] 语义、**可直接驱动 fail-closed 阈值**——BM25 的 TF-IDF 分数定不了拒答线
- **可背收束句** —— 「我的场景里，检测结果入口是精确 key 查表，不该用 RAG；症状描述入口是自由文本问诊，必须用 RAG——因为查询无 key、答案要溯源、语料不适合微调。双入口的划分本身就是答案。」

### 2026-10-08 · query 改写切片：评测暴露「改写不是银弹」

- **p06/p07 变差的根因（AI 分析，用户要求记录）** —— 以 p06 为例：turn2 原话「白天扒开根部土能抓到，灰黑色的小虫」裸检索命中白边地老虎 ✓；改写补上历史里的「玉米苗茎基部被咬断」（**指代补全是正确的**）后，top-3 反而变成亚洲玉米螟×2。根因不是「名称重叠」，恰恰相反——地老虎语料里寄主是泛化表述（不含「玉米」字样），而玉米螟语料大量出现「玉米」；BGE 是词面统计语义，补上正确的作物词后向量整体被拉向含「玉米」的语料块，压过了症状词匹配。p07 同理：「绿黑色」等规范词在麦蚜语料里未必精确对应，反而稀释了「麦粒瘪」这个原本直接命中的症状描述。**一句话：改写补全的事实是对的，但「更完整 ≠ 更贴语料」——改写器不感知语料分布，这是纯 LLM 改写（无语料感知）的结构性局限。**
