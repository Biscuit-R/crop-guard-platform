## 1. 项目定位

### 1.1 一句话

面向农业技术推广场景的**多用户 Web 平台**：上传作物照片 / 视频 / 摄像头实时画面，用 YOLO 模型识别病虫害，给出带标注的结果图、可检索的历史记录、以及可查防治方法的病虫害图鉴。

### 1.2 目标用户与场景

| 角色 | 使用场景 | 关键诉求 |
|---|---|---|
| 种植户 / 农技员 | 田间拍照，或举着手机对着叶片开摄像头 | 快；结果能看懂（中文名）；知道怎么治 |
| 农技推广站管理员 | 管理账号、审核讨论区、监管模型版本 | 权限边界清楚；操作可追溯 |
| 开发者（本人） | 训练出新模型后替换上线 | 模型可替换、版本可追溯、替换失败可回滚 |

**关键约束**：用户主要在田间用手机浏览器访问，网络条件差。这决定了前端不能假设长连接稳定，也不能把大计算量压给客户端。

### 1.3 明确非目标（Out of Scope）

这一节和「做什么」同等重要。

| 不做 | 理由 |
|---|---|
| **不做 AI 能力本身** | 不训练模型、不接入 LLM / RAG / 向量库。模型是外部产物（复用归档的 `model_67.pt` / `model_102.pt`），平台只负责**推理服务化**。本项目的考核点是工程能力。 |
| **不接真实短信网关** | 短信做成**可替换的 Provider 接口** + 一个 `console` 实现（开发期把验证码打到日志）。但**链路是真的**——见 FR-1.5。 |
| **不做分布式推理** | 单机多进程。不做 GPU 调度、不做 K8s、不做多机负载均衡。 |
| **不做训练可视化平台** | v1 的 `training/` 脚本保留为**离线工具**，不纳入 Web 服务。 |
| **不做移动端 App** | 只做响应式 Web。 |
| **不做多租户 / 组织架构** | 单租户，角色只有 user / admin 两档。 |

## 2. 功能需求

> 编号规则：`FR-<模块>.<序号>`。优先级 **P0** = 不做则项目不成立；**P1** = 对等 v1 必需；**P2** = 加分项。

### FR-1 账号与会话

#### FR-1.1 注册（P0）
- **描述**：用户名 + 邮箱 + 密码注册。用户名唯一且限定 `[a-zA-Z0-9_]`、3–20 字符；邮箱唯一；密码长度 8–128。
- **验收标准**
  - 用户名/邮箱重复时返回 409 与明确字段级错误，不泄露"该邮箱已存在但用户名可用"这类组合信息面
  - 注册成功即建立会话（v1 行为，保留）
  - 密码强度：最少 8 位；**拒绝常见弱口令**（v1 只要求 6 位且无强度校验 → `A-38`）
- **v1 证据**：`auth.py:37`（硬编码 `role="user"`，无法提权，**这点保留**）
- **v2 变更点**：密码策略收紧；错误码语义化

#### FR-1.2 登录与会话（P0）
- **描述**：用户名 + 密码换取访问凭据。
- **验收标准**
  - 凭据有效期**可配置**，默认 access token 2 小时
  - **必须支持服务端主动失效**（改密码、禁用账号时立即生效，不能等过期）
  - **登录失败限流**：同一账号 + 同一来源，连续失败 N 次后指数退避（v1 可无限暴力尝试 → `A-38`）
  - 凭据必须携带并校验**签发者与受众**
- **v1 证据**：`G-04`（`token_version` 机制，**这是 v1 最好的设计之一，v2 保留**）
- **v2 变更点**：有效期 24h → 可配置 2h；补限流；补 aud/iss 校验；**是否引入 refresh token 由 `ADR-003` 决定**（需求侧只要求"可服务端撤销"）

#### FR-1.3 登出（P1）
- **描述**：登出后该凭据立即不可用。
- **验收标准**：登出状态**必须自动过期**，不得无限累积（v1 的 `revoked_tokens` 表只增不删、无 TTL、且每次带凭据的请求都要查一次 → `A-12`）
- **v2 变更点**：吊销记录的存活期 ≤ 凭据剩余有效期

#### FR-1.4 修改密码（P1）
- **描述**：需提供当前密码；修改成功后**所有端强制登出**。
- **验收标准**：本人其它设备的会话在下一次请求时失效
- **v1 证据**：`G-04`

#### FR-1.5 手机号验证码（P0 · v2 新增真实链路）

> v1 有一份 SMS 演示代码（`sms.py`，188 行），验证码限流、原子消费、熔断都做得很扎实，但它**不与账号体系发生任何关系**：无表存手机号，验证通过后不签发任何凭据，且两个端点**都无鉴权**（`A-19`）。v2 把这条链路接通。

- **描述**：手机号 + 短信验证码，用于三个场景——**绑定手机号 / 手机号登录 / 找回密码**。
- **验收标准**
  - **验证码按用途隔离**：绑定、登录、找回的验证码互不通用（v1 是单一 key `sms:code:{phone}` → 同一个码可用于任意目的）
  - **验证码只能成功消费一次**，且消费是原子的（`G-01` 已有正确实现）
  - **验证码具有 TTL**，且首次写入时才设置过期
  - 限流三档全部保留：**同号 60 秒间隔** / **同号每日 5 次** / **连续错误 5 次锁定 10 分钟**（`G-07`）
  - **限流组件故障时必须 fail-closed**（拒绝服务，而非放行）——`G-03` 的语义，v2 保留
  - **不泄露手机号是否已注册**：`/send` 对已注册与未注册手机号返回完全一致的响应
  - **三个场景签发不同的凭据**：
    - 绑定 → 要求调用方**已登录**，把手机号绑到当前用户
    - 登录 → 要求该手机号**已绑定到某个启用状态的账号**，签发与密码登录等价的会话凭据
    - 找回密码 → 签发**一次性、短 TTL 的 reset ticket**，该 ticket **只能用于改密码、不能当会话凭据用**
  - 手机号在账号上唯一
- **v1 证据**：`G-01` `G-02` `G-03` `G-07` `G-08`（限流与原子性实现**直接复用**）；`A-19`（链路断裂，v2 修复）
- **v2 变更点**：新增 `phone` 到账号；验证码 key 按用途分区；`/verify` 从"返回成功消息"改为"签发真实凭据"；端点鉴权明确（`/send` 与 `/login` 公开但有严格限流，`/bind` 要求登录）

#### FR-1.6 角色与权限（P0）
- **描述**：两档角色 `user` / `admin`。
- **验收标准**
  - **每个端点的权限档位必须在代码中显式声明**（公开 / 登录 / 管理员），无默认可绕过路径
  - 角色变更**立即生效**，不等凭据过期（v1 已经是这样，因为判据查库 → `G-04` 的副产物，**保留**）
  - **不允许降级最后一个管理员**（v1 无此保护 → `A-31`）
  - 角色字段收到非法值时**必须显式报错**，不得静默忽略（v1 `admin.py:50-51` 的 `if` 无 `else`，传 `"superadmin"` 会返回"角色已更新" → `A-30`）
- **v1 证据**：`G-14`（首个注册用户自动成为管理员，用于冷启动，**保留**）

#### FR-1.7 管理员管理用户（P1）
- **描述**：列表 / 改角色 / 启用停用 / 删除。
- **验收标准**
  - 列表**必须分页**（v1 全量返回且含邮箱 → `A-13` 同类问题）
  - 不能修改自己的角色、不能禁用自己、不能删除自己（v1 已有，**保留**）
  - 禁用与删除时**所有端立即登出**（`G-04`）
  - 删除用户时其检测历史、帖子、评论按既有级联规则清理

### FR-2 病虫害检测

> **修正一个沿用的错误说法**：v1 常被称为"四种检测模式"，但 UI 上只有 **3 个模式**（`DetectionPage.vue:396-400` 的 `modes` 数组：image / video / camera）。"单图 / 批量"是 image 模式内的两个入口。死代码 `FunctionTabs.vue:40` 里还残留着第 4 个 tab，说明"四种模式"是重构前的概念。
> **v2 的定义**：**4 个检测能力**（单图 / 批量 / 视频 / 摄像头），**UI 组织为 3 个模式页签**。

#### FR-2.0 公共要求（P0）
- **验收标准**
  - 所有检测结果**必须同时返回英文 `class_name` 与中文 `chinese_name`
  - 结果必须标明**实际使用的模型版本**
  - 必须返回单次检测耗时
  - 上传大小限制：图片 50MB / 视频 200MB / 论坛图 10MB（v1 已有，**保留**）
  - 上传**必须流式落盘**，内存占用与文件大小无关（`G-06` 已有正确实现）
  - 上传文件类型按**内容嗅探**校验，不依赖扩展名与客户端 `Content-Type`（v1 只校验大小与后缀）
  - **检测失败也必须落库**，记录 `status=failed` 与错误原因，且清理已写出的半成品文件（v1 失败不落库、不清理 → `A-21`）
- **v1 证据**：`G-06`、`A-21`

#### FR-2.1 单图检测（P0）
- **描述**：上传一张图，返回标注后的结果图。
- **验收标准**
  - **原始文件名必须保留并落库**（v1 存的是 `temp_{uuid}.jpg`，导致历史记录里显示随机串、按文件名搜索永远搜不到 → `A-09`）
  - 进度：单张图片，同步等待
- **v1 证据**：`A-09`

#### FR-2.2 批量图片检测（P0）
- **描述**：一次上传多张图。
- **验收标准**
  - **单张失败必须隔离**，不影响同批其它图片，且**失败原因逐张返回**
  - 批量的整体响应**必须能表达"部分成功"**（v1 的 `success` 恒为 `true`，即使全部失败 → `A-24`）
  - **DB 失败不得污染后续图片**（v1 无 `db.rollback()`，一次 commit 失败会让整批剩余全部连锁失败，且前端看到的是"每张都失败" → `A-03`）
  - 批量处理有**并发上限**，且并发度可配置
- **v1 证据**：`A-03`、`A-24`

#### FR-2.3 视频检测（P0）
- **描述**：上传视频，返回标注后的视频 + 类别汇总 + 关键帧。
- **验收标准**
  - **按轨迹计数，不按帧计数**（同一只虫在 100 帧里只算 1 只）—— `G-12` 已有实现，**保留**
  - 跳帧间隔可配置（1–30，默认 5）
  - **逐帧/逐轨迹的框数据必须落库**，支持后续二次分析（v1 的 `boxes` 对视频恒为 `[]`，框数据只存在于结果 MP4 里 → `A-27`）
  - **结果视频编码器不可用时必须显式失败**，不能静默写出 0 字节文件
  - **响应模式：同步等待**。上传后阻塞直到处理完成再返回。
    - 理由：保持 v1 接口契约的对等性；改动面小；修的正是 `A-01` 那条阻塞事件循环的严重问题。
    - **代价（明确接受）**：长连接会占用 worker。因此必须同时满足 NFR-P2 的并发上限与 NFR-P3 的超时要求，并在文档中记录这是**已知取舍**。
- **v1 证据**：`G-12`、`A-01`、`A-27`

#### FR-2.4 摄像头实时检测（P1）
- **描述**：浏览器调用摄像头，实时把检测框叠在视频流上。
- **验收标准**（v1 是四种能力里唯一有真实前端算法的一条，**整套保留**）
  - 上传前**降采样到半分辨率 + JPEG q=0.5**，复用一个离屏 canvas（`DetectionPage.vue:915-930`）
  - 检测与绘制**解耦**：独立的 `requestAnimationFrame` 绘制循环，检测用固定间隔（v1 为 300ms）
  - **平滑**：按 `class_id` + IoU > 0.3 匹配后做 EMA（α = 0.6），并保留 600ms 内的"滞留框"（`DetectionPage.vue:861-911`）
  - **并发保护**：上一帧未返回时不发新请求
  - **连续 5 次失败自动停止**摄像头（`DetectionPage.vue:913, 951-954`）
  - 面板展示**累计物种清单**，而非单帧结果
- **v2 变更点**：以上逻辑必须从 1306 行的 `DetectionPage.vue` 抽成独立的 `useCameraDetection()`（见 `A-32`、NFR-M4）

#### FR-2.5 检测报告（P2）
- **描述**：把当前检测结果整理成一份报告展示。
- **验收标准**：若要保留，必须**能导出或落库**（v1 只是把内存状态拼成一个对象塞进弹窗，无导出、无落库，且视频分支带着一个从不渲染的 `key_frames` 字段 → `A-37` 同类）。**若无法明确用途，建议砍掉。**

### FR-3 检测历史（P0）

- **描述**：按用户隔离的历史记录列表、详情、删除。
- **验收标准**
  - 所有查询**必须带用户维度过滤**，越权访问结构上不可能（v1 已做到，**保留**）
  - 分页 + 关键词 + 状态筛选
  - **关键词必须能搜到原始文件名**（依赖 FR-2.1 保留原名 → `A-09`）
  - `status` 筛选**必须有真实语义**。v1 的 `status` 是死字段：所有写入路径都硬编码 `completed`，无任何代码写过其它值，导致 `success_rate` 恒为 100%、`status` 筛选永远只能匹配一种值（`A-20`）。v2 因为检测失败也落库（FR-2.0），`status ∈ {completed, failed}` 才有意义。
  - 批量删除。空数组返回参数校验错误（v1 返回 422，**保留**）
  - 类别名**必须显示中文**（v1 历史页直接渲染英文 `class_name`，而检测页与图鉴浮窗都用中文 → `A-34`）
- **v1 证据**：`A-09`、`A-20`、`A-34`

### FR-4 数据看板（P1）

- **描述**：统计卡片 + 最近记录。
- **验收标准**
  - **权限边界**：普通用户**只看个人**数据；全平台口径（总用户数、全站今日量）**仅管理员可见**（v1 把所有登录用户都能看到的全平台数据混在个人看板里 → `A-29`）
  - 统计**不得 N+1**：同类聚合应合并为常数条查询（v1 拆成 6 次独立查询 → `A-14`）
  - 结果可缓存，缓存失效时**静默回退到直连**（fail-open）—— `G-03` 语义，**保留**
  - 缓存键**按用户/权限范围隔离**，跨日自动更换
  - "今日"的时区口径**全项目统一**（v1 看板按 UTC、短信按北京时间，同一天边界差 8 小时 → `A-22`）
- **v1 证据**：`G-03`、`A-14`、`A-22`、`A-29`

### FR-5 病虫害图鉴（P1）

- **描述**：102 类病虫害的百科信息，公开可读；支持搜索与分面筛选；检测结果可跳转到对应条目。
- **验收标准**
  - **图鉴条目必须与模型类别索引绑定**，不允许"一份图鉴配所有模型"。v1 的 `data.yaml`（102 类）与 `data_balanced.yaml`（67 类）**同一 index 指向不同物种**，混用权重会让中文名映射整体错位（`A-07`）
  - 数据**不得硬编码在源码字面量里**（v1 是 1912 行 Python 字面量，无法后台维护），也不得每次请求重建全部对象（v1 `/pests/list` 每请求新建 102 个 Pydantic 对象 → `A-11` 同类）
  - 搜索与分面筛选在客户端完成（v1 已如此，**保留**——102 条数据量小，一次拉取合理）
- **v1 证据**：`A-07`、`A-11`

### FR-6 讨论区（P1）

- **描述**：**审核制 UGC**。用户发帖（可带图）→ 管理员审核 → 展示；支持评论、置顶、删除。
- **验收标准**
  - 新帖默认 `pending`，非 `approved` 的帖子**仅管理员可见**（v1 已做到，**保留**）
  - 列表**不得 N+1**（v1 对每条帖子各触发一次评论加载与一次用户加载，`page_size=50` 时最多 101 次查询 → `A-13`）
  - 请求体**必须走 schema 校验**（v1 评论接口收裸 `dict`，绕过了已定义但从未使用的 Pydantic 模型 → `A-11`）
  - 审核意见字段语义唯一：v1 在 `approved` 时也写 `admin_note`，与"拒绝理由"共用字段（`A-24` 同类语义混用）
  - 删除自己的帖子与删除任意帖子**权限分离**（v1 已做到，**保留**）
- **v1 证据**：`A-11`、`A-13`

### FR-7 模型管理（P0）

- **描述**：查看当前模型状态、列出可用模型、切换模型、查看版本历史。
- **验收标准**
  - **切换模型与重载模型必须仅限管理员**。v1 这两个端点只要求登录，**任何普通用户**都能让全平台切换到另一个模型（`detection.py:181, 203`，已实测确认 `detection.py` 全部 9 个端点都用 `get_current_user`，无一处 `get_current_admin`），且切换支持模糊匹配 `glob("*{version}*.pt")`，传 `"model"` 即可命中 → `A-02`
  - **请求级模型选择**：单次检测可指定已注册的模型版本，**但仅作为本次请求的覆盖，不产生全局副作用**。v2 需支持同时持有多个模型实例（带 LRU 上限与加载锁）。
    - v1 的 `model_name` 参数被完全忽略（`detection.py:44` 是 `current_model_version or model_name`），默认值 `"pest-v1"` 是**虚构的**，不匹配任何真实文件（`A-10`）
  - **模型热更新保留**：训练脚本覆盖模型文件后自动生效（`G-11`），但必须**可审计**——记录何时、由谁、从哪个版本切到哪个版本
  - **版本历史必须有真实数据源**。v1 读 `training/versions.json`，该文件**从不存在**，所以 `/models/history` 永远返回空数组（`A-10`）。v2 的版本记录必须落库，含训练超参、mAP 等指标
  - 模型文件**不入 git**（v1 已如此，**保留**）
- **v1 证据**：`G-11`、`A-02`、`A-10`

---

### FR-8 数据集格式转换工具（P1）

- **描述**：上传 ZIP 数据集（VOC/XML、COCO、CSV），转成 YOLO 格式，打包下载。
- **验收标准**
  - **上传必须流式落盘**，不得整包读入内存（v1 `dataset.py:58-59` 一次性 `await file.read()`，不走同仓库已有的分块限流 → `A-05`）
  - **解压产物有总大小与文件数上限**（防 ZIP 炸弹。v1 解压前只校验了路径穿越，没有大小上限 → `A-05`）
  - 解压路径穿越防护**保留**（`G-05`，优于多数同类实现）
  - **训练/验证集必须真实划分**。v1 生成的 `data.yaml` 中 `val: images/train`，与 `train` 完全相同，且所有转换器只往 `images/train` 写，没有验证集。用该产物训练会导致**验证指标严重虚高**（`A-06`；此条由两个独立分析各自发现，可视为已确认）
  - **类别名解析必须跳过注释行**。v1 `load_classes` 只过滤空行，而官方示例文件 `classes_example.txt` 自带 3 行 `#` 注释（含一行"使用方法"的调用命令），按文档执行会让类别 0/1/2 变成注释文本，**102 类整体偏移 3 位**（`A-17`）
  - **转换结果必须与目标模型的类别表校验一致**，不一致则拒绝并报出差异（这是 `A-07` 的根因——类序不一致却无人校验）
  - **临时目录必须清理**，且同一用户的并发转换**不得互相破坏**（v1 的 `work_dir` 按 user_id 持久复用、从不清理，同用户并发两次会互相删除对方目录 → `A-28`）
  - 下载按**转换任务 ID** 寻址，不按用户 ID（v1 按 `user_id` 拼 URL，且页面挂载时不拉取用户信息，硬刷新后直接进该页会导致"转换能成功、下载必失败" → `A-35`）
- **v1 证据**：`G-05`、`A-05`、`A-06`、`A-17`、`A-28`、`A-35`

---

### FR-9 前端壳（P1）

- **描述**：登录 / 注册 / 主框架 / 路由。
- **验收标准**
  - **鉴权状态单一来源**：凭据的读写只能有一处实现（v1 散落在 `utils/request.js:12`、`router/index.js:98`、`stores/user.js:18` 三处独立读取，清除逻辑在 4 处重复 → `A-33`）
  - **必须补齐 404 通配路由**（v1 未匹配路径渲染空白页 → `A-36`）
  - 角色相关的 UI（管理员菜单、审核 Tab）**不得出现"晚一拍"**：v1 的 `userInfo` 不持久化，首屏渲染时为空，管理员会短暂看到普通用户视图（`A-33` 同类）
  - **错误提示不得重复**：v1 的 401 处理在跳转登录后仍 reject，各页 `catch` 再弹一次业务文案，把"登录已过期"掩盖成"检测失败，请稍后重试"（`A-16`）
  - 关键操作的长任务**必须有可关闭的加载态**：v1 模型切换失败时全屏遮罩永不关闭，整页被蒙住且只能刷新（`A-04`）
- **v1 证据**：`A-04`、`A-16`、`A-33`、`A-36`

## 3. 非功能需求

> v2 相对 v1 的**主要增量在这一节**。v1 功能齐全，工程规范几乎为零（零测试、零 CI、无生产部署路径）。

### NFR-P 性能与并发

| 编号 | 要求 | 验收标准 | v1 证据 |
|---|---|---|---|
| NFR-P1 | **CPU 密集的推理不得阻塞请求调度** | 推理进行中，健康检查端点的 p99 < 100ms | `A-01`（v1 全部检测端点都是 `async def` 却直接调同步推理，全库无一处 `run_in_executor`，已实测确认；单个请求推理期间所有端点排队） |
| NFR-P2 | **推理并发有上限且可配置** | 并发上限默认 = CPU 核心数；超限请求排队而非耗尽资源 | `A-01`（v1 用 `threading.Lock` 全局串行化，并发吞吐 = 单次推理速度） |
| NFR-P3 | **所有外部调用有超时** | DB 语句超时、缓存读写超时、模型推理超时均可配置且有默认值 | `A-45`（v1 的 DB 无 statement_timeout，慢查询可无限期占用连接） |
| NFR-P4 | **列表接口无 N+1** | `page_size` 取最大值时，SQL 语句数为常数 | `A-13`、`A-14` |
| NFR-P5 | **上传内存占用与文件大小无关** | 上传 200MB 视频时进程 RSS 增量 < 50MB | `A-05`、`G-06` |

### NFR-S 安全

| 编号 | 要求 | v1 证据 |
|---|---|---|
| NFR-S1 | **每个端点的权限档位显式声明，无默认可绕过路径** | `A-02` |

## 5. v1 审计结论摘要

完整证据见 **`docs/v1-audit.md`**。

v1 代码规模：后端 26 个 Python 文件 6385 行 + 前端 7172 行 JS/Vue（不含依赖）。

| 分级 | 数量 | 代表问题 |
|---|---|---|
| 🔴 P0 | 7 | 事件循环阻塞、模型管理越权、无事务边界、UI 永久卡死、ZIP 炸弹、`val` 指向 `train`、两套模型类序不一致 |
| 🟡 P1 | 38 | 413 被吞成 500、原文件名丢失、约 600 行死代码、看板泄露全平台数据、零测试零 CI、无生产部署路径 |
| 🟢 好设计 | 17 | Lua 原子消费、fail-open/fail-closed 双模降级、熔断、`token_version` 全端登出、ZIP 路径穿越防护、视频跨帧追踪、摄像头前端管线 |

**对 v2 的含义**：v1 的问题不在"功能没做完"，而在**工程规范缺失**——功能覆盖很全，但零测试、零 CI、无生产部署路径、无统一事务边界、无分层。v2 的增量主要在 §3，§2 大部分是对等 + 定点修复。
