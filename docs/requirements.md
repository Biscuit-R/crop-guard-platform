# crop-guard-platform v2 · 需求

> 2026-09-23 ｜ 阶段 1 产物 ｜ 每条均逐条确认 ｜ 上游 `docs/workflow.md`

## 是什么

单机部署的多用户 Web 平台：上传作物照片 / 视频 / 摄像头画面，用 YOLO 模型识别虫害，给出标注结果图与可检索历史。**农业是外壳** —— 考核点是工程能力与 AI 工作流。

> **范围用词（2026-10-03）**：全项目统一用**虫害**，不用「病虫害」。检测模型与语料均为虫/螨（102 类），**不含真菌/细菌/病毒病害** —— 用「病虫害」会造成范围歧义。

## 做什么

**核心 · 做深**（有测试、进 CI、有可量化验收）

| 模块 | 范围 | 深在哪 |
|---|---|---|
| 账号与会话 | 注册（用户名 + 密码 + 手机验证码）/ 登录 / 登出 / 改密；两档角色；凭据可服务端撤销 | 限流、并发安全、凭据语义 |
| 虫害检测 | 单图为主线；批量 / 视频 / 摄像头为**可选项**（见「取舍」的砍序） | 推理不阻塞调度、失败也落库 |
| **知识问答（RAG）** | **双入口**：① 检测结果 → 治理方案 ② 症状描述 → 虫害检索 | 检索质量与拒答语义、生成可溯源、降级分级 |
| 检测历史 | 按用户隔离的列表 / 详情 / 删除 | 查询不 N+1、越权结构上不可能 |
| 模型管理 | 状态 / 切换 / 版本历史（仅管理员）；热加载 | 权限边界、审计记录、类别表与模型绑定 |

**外围 · 做浅**（**写测试，但不追性能与工程深度**）
数据看板 · 讨论区 · 前端壳（登录 / 注册 / 主框架 / 路由 / 404）

**设计亮点**（刻意保留，用于讲述）
**按故障语义分级的降级**：缓存不可用 / LLM 生成不可用 → **fail-open**（降级服务：直连、或只返回检索原文）；认证 / 限流 / **检索置信度不足** → **fail-closed**（拒绝，因为猜错有真实后果）。**分级依据是「故障的代价」，不是配置开关 —— 这是判断，不是配置。**

## 不做什么

| 不做 | 理由 |
|---|---|
| AI 能力本身 | 不训练模型、不接 LLM / RAG / 向量库。平台只做推理服务化 |
| 虫害图鉴的独立浏览页 | 图鉴**数据**改作 RAG 语料使用（见「做什么」）；独立的浏览 UI 不做，技术含量最低。**保留类别名映射** —— 结果要显示中文名 |
| **作物病害**（真菌 / 细菌 / 病毒） | 检测模型与语料均为虫/螨（102 类），**范围锁定在虫害**。项目名原为「病虫害」，2026-10-03 统一改为「虫害」以消除范围歧义 |
| 模型微调 / 训练 | 场景要的是**事实检索**，而微调改变的是能力与风格 —— 用微调注入事实会遗忘、会混淆、更新一条要重训。**不是「没条件做」，是「用错了工具」**。改为准备选型论证，理由见 `docs/decisions.md` D9 与 `docs/notes.md` |
| 数据集格式转换工具 | 偏离检测主线 |
| 真实短信网关 | 验证码随机数生成，Redis 管过期与限次。**链路是真的，网关是假的** |
| 分布式推理 / GPU / K8s | 单机 demo 足够 |
| 移动端 App | 只做响应式 Web |

## 成功标准

**核心模块的每条标准都必须能跑出结果，并有测试证明。**

| 模块 | 标准 |
|---|---|
| 账号 | 改密后所有端立即失效；登录连续失败 N 次后拒绝；凭据有效期可配置 |
| 检测 | 推理中健康检查 p99 < 100ms；上传 200MB 时 RSS 增量 < 50MB；失败也落库并清理半成品；类型按内容嗅探校验 |
| 历史 | `page_size` 取最大时 SQL 语句数为常数 |
| 模型管理 | 普通用户调切换接口返回 403；切换留审计记录；class 数不符时拒绝加载 |
| **知识问答（RAG）** | 30 条症状评测集 top-3 命中率 ≥ 80%；**6 条明显无关问题（B1）拒答率 = 100%**（4 条农业相关但语料没有的问题 B2 允许落入中间档「作答 + 标注」，2026-10-03 拍板，见 `rag-eval-set.md` B 节）；答案可溯源到图鉴条目；断开 LLM API 时降级返回检索原文；检索 P99 < 200ms；一条命令重建索引 |

**全局**：`docker compose up` 一键起全栈；CI 跑测试与依赖扫描。

## 规模、时间与取舍

- 单机 demo，**保留后续上真实服务器的可能性**
- 时间盒 **2026-10-01 → 10-17（华为线下面试）＝ 16 天**
- **每日投入 ≥ 4h（2026-10-01 确认，后期可更多）→ 合计至少 64h，乐观 80–96h**
- 扣除面试准备约 30h（八股 ~15h / 白板手撕 ~10h / 项目与模拟 ~5h）→ **可编码约 34–66h**
- 编码工作量估算：阶段 3 ~5h + 账号 ~8h + 单图检测 ~6h + 历史 ~3h + 模型管理 ~4h + **RAG ~15h** + 收尾 ~3h = **约 44h → 可以容纳，但余量不大**
- **进度调节阀（双向，预先定死）**：
  - **落后**时依次砍：① 摄像头 → ② 视频 → ③ 批量 → ④ 模型管理 → ⑤ 检测历史

  - 账号 / 单图检测 / **知识问答（RAG）** / 阶段 3 框架 —— **两个方向都不动**
- **检查点 2026-10-10**：核对进度。落后则执行砍序，超前则加回摄像头；**并核对 GitHub 是否已推送**（见下条）
