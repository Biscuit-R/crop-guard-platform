# 本项目的工作流

> 2026-09-22 ｜ 定义「这个项目怎么用 AI」。执行时照着走，偏离要说明理由。
> 与 `CLAUDE.md` 的分工：`CLAUDE.md` 给 agent 读（硬约束），本文件给人读（流程与理由）。

## 为什么需要这份文档

项目的目的不只是做出平台，还要知道 **AI 在哪些环节真的帮上了忙、在哪些环节只是看起来在帮忙**。

所以每选一条流程、每砍一条流程，都要能说出理由。**理由才是面试素材，流程本身不是。**

## 阶段划分

| 阶段 | 产物 | 人工闸门 |
|---|---|---|
| 0 · 工作流设计 | 本文档 + `CLAUDE.md` | 确认即过 |
| 1 · 薄需求 | 一页纸 ≤60 行：做哪几个模块 / 不做什么 / 成功标准 | **逐条确认**，不确认的不进文档 |
| 2 · 技术选型 | 选型记录 —— 只写真正有分歧的决策，不分歧的只记结论 | **逐条拍板** |
| 3 · 框架搭建 | 能跑通的空壳：分层、配置、CI、测试骨架、容器 | 跑给人看 |
| 4 · 垂直切片 | 每片 = 一个端到端功能 | 开工前验收标准由人确认 |
| 5 · 收尾 | 部署路径、README、复盘汇总 | — |

**垂直切片**：按功能端到端切分（登录 / 单图检测 / 历史 / …），不按层切分。每个切片自带它的数据、接口、界面、测试。

## 人工闸门（不可协商）

1. 需求每条 —— 人确认才进文档
2. 选型每个决策 —— 人拍板才记录
3. 每个切片开工前 —— 验收标准由人确认「可执行」
4. 删改文件、改 `.env`、装依赖 —— 一律先问
5. AI 不得自称完成 —— 必须有可执行的检查输出为证
6. 产出代码的一方不得自己验收

## 复盘格式

每阶段末一条，四行，记录在 **`docs/notes.md`**：

```
AI 做了什么 →
哪里帮上忙（具体）→
哪里添乱（具体）→
我做了什么判断
```

**第四行是关键。** 没有「我做了什么判断」的复盘，就只是流水账。

第四行由人来说 —— AI 可以提示「这里你做了判断」，但不得代写。

## 这份工作流的已知弱点

诚实记录，避免把它当成已验证的结论：

- **单人项目 = 缺少真实审查压力。** 代码审查被简化，这是可预见的最大弱点。
- **阶段划分是预设的，不是发现的。** 真实项目里阶段边界会模糊，届时应当调整而不是硬套。
- **闸门 5 需要人来执行。** 人偷懒它就失效 —— 这本身就是值得记录的失效模式。
