## 第 0 部分 · 总纲：一句话打通所有概念

如果这份材料你只记一句话，记这句：

> **LLM 是一个无状态、上下文有限、且会一本正经胡说八道的函数。所有围绕它的技术，本质上都在解决同一个问题：怎么把正确的信息，塞进那个有限、无状态、又会编的模型里。**

拆开看这三个性质，会推出后面所有的技术：

| 性质 | 含义 | 推出的技术 |
|---|---|---|
| **无状态** | 模型不记得上一句。所谓"多轮对话"是把历史全部重发 | 上下文管理、压缩、缓存 |
| **上下文有限** | 一次能塞的 token 有上限 | 切分、检索（RAG）、摘要 |
| **会编（幻觉）** | 它预测"最像答案的文本"，不是查数据库 | 防幻觉提示、引用溯源、评测 |

再往后：

| 技术 | 一句话 |
|---|---|
| **Prompt 工程** | 怎么把话说清楚，让模型输出你想要的东西 |
| **上下文工程** | 怎么在有限的窗口里，动态管理该给模型看什么 |
| **RAG** | 从外部知识库检索相关内容，塞进上下文 |
| **Agent** | 让模型在循环中调用工具，自主完成多步任务 |
| **MCP** | 把"模型连接工具"这件事标准化 |
| **AI 辅助开发** | 把人写代码变成人编排 Agent + 监督 |

### 概念地图

```
用户提问 / 任务目标
      ↓
【检索】找到相关信息            ← 关键词：RAG、Embedding、向量库、重排
      ↓
【上下文组装】把信息拼成 prompt  ← 关键词：上下文工程、防幻觉、引用
      ↓
【LLM 推理】生成回答 or 决定调工具 ← 关键词：Token、温度、幻觉
      ↓
【工具执行】跑代码/查库/调 API    ← 关键词：Function Calling、MCP
      ↓
【循环】观察结果，继续或结束      ← 关键词：Agent、ReAct
      ↓
【验证】确认没出错                ← 关键词：评测、Oracle、独立验证
```

## 第 1 部分 · LLM 基础

### 1.1 本质：下一个 token 的预测器

LLM 的核心机制可以极度简化为一句话：

> **输入一段文本，输出"下一个 token"的概率分布。循环调用它，就生成了整段回答。**

这就是 **自回归生成（autoregressive generation）**。它不"思考"、不"查资料"、不"理解"——它在做一件统计学上的事：根据训练数据，预测什么样的下一个词最合理。

**为什么这个认知重要**：它解释了 LLM 的一切优点和缺陷。

- 优点：见过海量文本，所以"像人写的"回答对它来说很容易
- 缺陷：它没有事实数据库。它是在**生成"看起来像答案的文本"**，而不是**查找真正的答案**

底层的 **Transformer** 架构提供的是"注意力机制"——让模型在处理每个词时，能权衡句子里其他所有词的重要性。这也是为什么长上下文里，**开头和结尾的信息更容易被注意到，中间容易被忽略**（Lost in the Middle）。这个现象后面会反复出现。

### 1.2 Token：计价与容量单位

Token 是**介于字符与单词之间的子词（sub-word）单位**，是模型真正"看见"的东西。

**为什么不用字节或单词**：用字节 → 序列太长，而注意力是 O(n²)，算力爆炸；用单词 → 词表爆炸（英语常用词超 17 万，加上术语、人名、URL、代码需要数百万），还会产生未登录词。**子词是折中**。

**分词机制：BPE（字节对编码）**。从最小单位开始，反复把最高频的相邻 pair 合并成新 token，直到词表达标（通常 5 万–20 万）。结果：

- 高频词（`the`、`Hello`）是**单个 token**
- 罕见词被拆成片段（`unbelievable` → `un` + `bel` + `ievable`）
- **同一个词在不同位置是不同的 token**：`" red"`（带前导空格）、`" Red"`、`"Red"` 是三个不同 ID

最后一条直接解释了 1.6 节的一个现象：**prompt 里一个空格的变化都可能让缓存失效**。

#### ⚠️ 中文的 token 劣势（对你尤其重要）

同样的语义内容，**中文消耗的 token 通常显著多于英文**。三层原因：

1. **UTF-8 字节数**：英文字母 1 字节，**汉字 3 字节**
2. **训练语料以英文为主**：早期 tokenizer 的 BPE 从英文语料建立，汉字太罕见、没被合并成高频组合。GPT-2 tokenizer 下一个汉字要 2 个 token，**效率只有英文的一半**
3. **实测**：约 1 个汉字 ≈ 1–2 token，1000 字中文段落可能消耗 1500–2000 token。Petrov 等（NeurIPS 2023）测 17 种语言，**缅甸语约需英语的 15 倍**

**改进方向**：**字节级 BPE + 大词表**（DeepSeek-V3/V4 用 128K 词表）已大幅缩小中英差距。ACL 2026 提出的 **parity ratio**（某语言每字符 token 数 ÷ 英文）显示：老旧 tokenizer 在 CJK 上差异极大，**新的大词表 tokenizer 已接近 parity**。

**实践含义**：
- 中文用户的**等效可用上下文更小、单位成本更高**
- **不同模型的同一段文本 token 数不同** → "每百万 token 单价更低" ≠ 总成本更低
- ⚠️ **迁移模型时要重新基线化 token 计数**：Sonnet 4.6 → Sonnet 5 因换新 tokenizer，**相同文本约多 30% token**

**为什么必须关心 token**：
- **定价**按 token 算，输入输出**分别计价**（输出通常贵 3-5 倍）
- **上下文窗口**按 token 算
- 代码、JSON、结构化数据的分词效率通常低于自然语言
- ⚠️ **reasoning token（推理模型的内部思考）同样计费**——`thinking.display` 只控制可见性，思考照常发生、照常收费

准确计数要用厂商的计数接口（如 Anthropic 的 `POST /v1/messages/count_tokens`），**不要用第三方估算库**。

### 1.3 上下文窗口（Context Window）

模型一次能"看到"的最大 token 数。**请求里的一切都计入**：system prompt、`messages` 里每一条（含工具返回结果、图片、文档）、**你的工具定义本身**、以及模型的输出（**含扩展思考的 token**）。

用量在响应的 `usage` 字段里查；开启缓存时会拆成 `input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens`——**三者都计入窗口**。

**三个必须知道的点**：

1. **它是"工作记忆"，不是"长期记忆"**。窗口之外的内容模型完全看不见。所谓"模型记得"是假的——是你的代码把历史重新发了一遍。
2. **塞得越满，质量越差**。而且**不是线性衰减**（见下）。
3. **成本随长度增长**。历史每轮重发，朴素累积的 token 成本是**二次增长**——这是 Agent 场景烧钱的主因之一。

当前主流模型窗口量级：**1M token 已成中端标配**（见附录 A）。

#### ⚠️ 关键认知：标称窗口 ≠ 有效窗口

**这是 2026 年最需要在面试里讲清楚的一点。**

**Lost in the Middle**（Liu et al., TACL 2024）的经典发现：

- 模型对**开头**（primacy bias）和**结尾**（recency bias）的信息利用最好
- 信息位于**中间**时性能显著下降，形成 **U 型性能曲线**
- 多文档问答中，相关信息放中间时 **GPT-3.5-Turbo 的表现甚至低于它闭卷作答的水平**
- **显式长上下文模型同样受影响**——"扩展了上下文"不代表"更擅长使用上下文"
- 检索文档从 20 篇加到 50 篇，准确率只有边际提升

**Context Rot**（Chroma Research, 2025；18 个前沿模型、约 19.4 万次调用）：

- **性能随输入长度增加持续下降，远在窗口填满之前就开始**——200K 窗口的模型在 50K token 时就出现明显下滑
- 下降可能是**突变的，而非渐进的**
- 反直觉：模型在**随机打乱的文本**上表现**优于**逻辑连贯的文档——结构一致性反而损害性能
- 真实场景（LongMemEval，约 113K token 聊天历史）：所有模型在**聚焦型 prompt**（只给相关信息）上显著优于**全量 prompt**
- 核心结论：**更大的窗口不能阻止 context rot——问题是噪声累积，不是容量不足**

**2026 年实测（⚠️ 第三方汇总，非厂商官方）**：

- 有效上下文通常只有标称值的 **30–50%**
- 声称 200K 的模型在约 **130K 处变得不可靠——是突然失效，不是渐进衰减**
- **位置偏差**：准确率会因为信息摆放位置不同而波动 **20–25%**

**实践建议**：

- **关键指令放开头，关键事实放结尾**，检索内容放中间
- 主动做**上下文策展**，而不是"能塞就塞"
- **10K token 的精挑检索，常常胜过 100K token 的粗暴堆料**
- 超了会怎样：请求阶段超限直接 **400 拒绝**；输出侧达到 `max_tokens` 会截断；图片/文档另有体积上限（可能**先触及体积上限而非 token 上限**）

**官方缓解手段**：

- **服务端压缩**：接近阈值时自动摘要历史（Claude 默认触发阈值 150K）。关键：必须回传**完整的 `response.content`**，只回传文本会静默丢失压缩状态
- **上下文编辑**：清除旧的工具结果或思考块——被称为"最轻量、最安全的一刀"
- Claude Code 在 **95% 容量时自动压缩**

### 1.4 采样参数

模型输出的不是确定的词，是概率分布。采样参数控制怎么从这个分布里挑。

**执行顺序**：先按 `top_k` 取概率最高的 K 个，再按 `top_p` 累积概率过滤，最后用 `temperature` 调整后的分布采样。同时启用时，**逐步应用最严格的那个约束**。

| 参数 | 控制什么 | 什么时候调 |
|---|---|---|
| **temperature** | 随机性。低=保守确定，高=多样发散 | 事实/代码/结构化输出 → 低；创意写作 → 高 |
| **top_p** | 从累积概率前 p% 的词里采样 | 比 temperature **更自适应**（模型确定时自动收窄候选集），二选一时**优先 top_p** |
| **top_k** | 硬性截断为概率最高的 k 个 | 较少用 |
| **max_tokens** | 单次输出上限 | 设太小会截断，导致重试反而更贵 |

#### ⚠️ 2026 年重大变化：推理模型正在移除采样参数

**这条必须知道，否则会直接踩 400 错误。**

从 **Claude Opus 4.7 和 Sonnet 5 起，`temperature` / `top_p` / `top_k` 已从 Messages API 中移除**。传入非默认值直接返回 **HTTP 400**（错误信息形如 "`temperature` is deprecated for this model"）。受影响前缀包括 `claude-opus-4-7`、`claude-opus-4-8`、`claude-opus-5`、`claude-sonnet-5`、`claude-fable-5`、`claude-mythos-5`。较早模型（Claude 3.x、Opus ≤ 4.6、Sonnet ≤ 4、Haiku ≤ 4）仍然接受。

**官方理由**：这些采样参数**与推理模型的内部逻辑不再兼容**。OpenAI 从 o 系列起也改用 `reasoning_effort` 而非 temperature。

**替代旋钮**：**effort 参数**（`low`/`medium`/`high`/`xhigh`/`max`）控制思考深度与 token 花费。在推理模型上这是更有效的"质量 vs 成本"旋钮。

**三条实用规则**：
1. **先查目标模型是否还支持采样参数**——盲目沿用旧代码会直接 400
2. 想调质量/成本，**调 effort，不要调 temperature**
3. 不要把 temperature 当"创造力开关"——它只是让分布变平坦，**不理解语义**

**⚠️ 另一个常见误解**：**即使 temperature = 0，LLM 也不是完全确定的**。浮点运算顺序、批处理、基础设施差异都会带来波动。所以"温度设 0 就能复现"是错的。

**面试提示**：问"怎么保证输出稳定"，正确答案有三层——
1. **结构化输出**（用 JSON Schema 做约束解码，非法输出在采样层"字面上不可能发生"）
2. **effort 与模型选择**，而不是 temperature
3. **外部验证**（测试、类型检查）——这才是最可靠的

### 1.5 幻觉（Hallucination）

**定义**：模型生成的内容语法通顺、语句流畅，但与事实不符且得不到外部证据支持。**它不是偶发口误，而是系统性偏差。**

**为什么会发生**：模型在生成"最像答案的文本"。它优化的**不是事实真相，而是语句的合理与流畅**。

一篇 2025 年 arXiv 论文的表述极为精准：

> GPT-3-175B 在 TruthfulQA 上真确率 58%，人类基线 94%——**"模型并非在训练失败，它精确地实现了 MLE 所指定的目标"**；更大的模型更完整地学到了训练分布，**包括其中的虚假内容**。

所以"模型变大了就更真实"是错的——**幻觉率与规模不是简单反比**。

**为什么模型"宁可编造也不说不知道"（⭐ 很好的面试素材）**：

现行多数评测采用**二元评分**：答对 1 分，答错或弃答 0 分。OpenAI 于 2026 年 4 月发表于《自然》的研究指出：**弃答永远是 0 分，而猜答案至少有得分机会，因此"永远猜"是数学上的最优策略。**

实例：SimpleQA 中 o4-mini 几乎回答所有问题（错误率超四分之三），GPT-5-mini 常选择放弃（错误更少），但**前者得分反而更高**。

这也解释了为什么"允许模型说不知道"是一个**从激励层面修正**的干预，而不只是提示技巧。

**工程上的缓解手段**（按有效性排序）：

1. **允许说不知道**——显式给模型承认不确定的许可，**并提供一个固定的兜底话术**。官方文档称这个简单的技巧能**大幅减少虚假信息**
2. **给依据 + 引文锚定**——把资料放进上下文，要求"只根据资料回答"。对 >20k token 的长文档，先让模型**逐字摘录引用**，再**只基于这些引文**做分析
3. **引用溯源验证**——要求为每个论断引用支撑原文，逐条核对，**撤回没有引文支持的论断**
4. **结构化输出**——约束输出格式，减少自由发挥空间
5. **外部验证**——用独立机制检查输出（最可靠，详见第 5 部分）
6. 降低 temperature / effort——有效但作用有限，**不是主要手段**

#### ⚠️ 重要认知：RAG 不能根除幻觉

即使给了**完全正确**的上下文，模型仍可能产生"有依据但结论错误"的输出。这被称为**语境不忠（context infidelity）**：

- 模型检索到了正确信息，却**未能把生成锚定于该信息**，反而退回参数化先验
- **即使模拟完美检索（oracle-perfect retrieval）**，在多跳难题上该现象仍以 **15%–30%** 的比例存在
- 机制解释：检索到的上下文与模型自身先验**在注意力中竞争**；当模型偏好流畅续写时，先验获胜（"**先验放大循环**"）
- ⚠️ **反直觉发现**：一个受控复现测试显示，**显式的文档引用与源锚定并不能可靠防止编造**——这挑战了"给更好数据/更长上下文即可解决"的假设
- ⚠️ **Chain-of-Thought 可能反而有害**：它可能让模型"推理着远离证据"

**⚠️ 另一个负面发现**：基于嵌入相似度和 NLI 的幻觉检测器**不是可靠的安全闸门**——最难检测的幻觉"在语义上与忠实回答无法区分"。

**一句话**：**幻觉不是 bug，而是 next-token prediction 目标的必然副产品。** 研究者的目标是"减少"而非"根除"。

> **面向使用者的三条准则**：① 提问划定明确范围；② 关键信息溯源核实；③ 重要事项交叉验证。

### 1.6 无状态性与多轮对话

**LLM API 在设计上是无状态的——模型不"记得"之前的对话轮次。** 每一次请求都必须包含累积的完整历史：system prompt、之前的用户消息、之前的模型回复、工具调用结果。

**"多轮对话"完全是应用层实现的假象。**

**为什么这样设计——这既是优点也是负担**：

- 优点：可水平扩展、可任意负载均衡、**无需会话亲和性**——任何一台推理服务器都能处理任何请求
- 负担：**所有记忆/状态管理都必须在应用层实现**

**三个工程后果**：

1. **对话越长越贵越慢**——历史 token 每轮重复计费。AI 编程工具还会额外重发庞大的 system prompt（配置文件、插件、MCP 工具定义），**一条一句话的消息可能意味着数万输入 token**
2. **两类成本同时增长**：金钱（输入 token 累积）和**延迟**（输入越多，首个 token 时间 TTFT 越长）
3. **Agent 循环中这复利式恶化**：单个 agent 任务消耗的 token 常达单轮聊天的 **50–100 倍**。这是 Agent 场景烧钱的主因

#### Prompt Caching（提示缓存）——首要解药

**原理**：服务端缓存**未变化部分**请求的 KV-cache 状态；当新请求共享同一前缀时，**只计算新增的后缀**。

- **成本**：缓存读取的输入 token 价格约为**全新输入的 10%**（约 90% 折扣）
- **延迟**：TTFT 大幅下降（有来源给出缓存前缀上约 80% 更快）
- **为什么和无状态天然契合**：正因为 API 无状态、应用每轮都发历史，**只要保持历史顺序稳定**，就自动创建了可复用的前缀

**实现要点**：

| 要点 | 说明 |
|---|---|
| **稳定内容放前面** | system prompt、指令、参考文档放开头；变化的内容（最新问题、时间戳、用户 ID）放末尾 |
| **前缀必须逐字节相同** ⭐ | 第 N 个位置任何变化都会使该位置之后的缓存**全部失效**——连 JSON key 重排或一个时间戳都会。回到 1.2 节：**一个空格都会改变 token** |
| **有最小长度门槛** | 太短的前缀永远不会被缓存。Anthropic 显式缓存在部分模型上需约 4096 token（Opus 5 降为 512） |
| **有断点数量上限** | Anthropic 为显式 `cache_control`，**每次请求最多 4 个断点** |
| **验证方式** ⭐ | 检查 `usage.cache_read_input_tokens`——**若在重复请求中始终为 0，说明有"静默失效源"**（system prompt 里有 `datetime.now()`、JSON 未排序、工具集变化等） |

**⚠️ 缓存 TTL 问题（容易被忽略）**：

- 厂商缓存**几分钟内就会过期**（Anthropic 默认 5 分钟，有付费 1 小时档；OpenAI 5–10 分钟无活动后清除）
- 这对**轮次间会暂停的 agent 工作流**（跑工具、构建、人工审批）影响最大
- 一旦暂停超过缓存寿命，后续请求按**全价 + 全延迟**计费，且**整个累积对话必须重新缓存**
- 应对方案是 **keepalive**：暂停期间用定时器重发完全相同的前缀并最小化生成，刷新 TTL。跨厂商测量显示 30 秒 keepalive 能保持 **≥98% 的 prompt token 处于缓存状态**

**降本杠杆（按有效性排序）**：

1. **保持上下文小** ⭐——被描述为**最有效的单一成本杠杆**。因为即使打 9 折，缓存读取（每次调用 10 万–数十万 token）仍主导总成本
2. **防止缓存过期**——一次 10 万 token 的缓存重建非常昂贵
3. **把重活委派给子任务**——隔离的小上下文减少缓存读取量
4. **精简 system prompt**——删掉未使用的插件 / MCP server / skills
5. **选择轻量工具**——Grep/Glob/部分读取给上下文增加的负担远小于全文件读取，**而这些 token 会在后续每次调用中被重新计费**

**会话重置策略**：当上下文很大且缓存已冷（空闲 ≥ TTL）时，跑一个 checkpoint 轮次持久化状态，然后开一个**全新会话**——因为过期后下一轮无论如何都要重新上传完整记录，**全新小上下文同样便宜，还白得一个干净起点**。

### 1.7 提示工程核心技巧

**通用构建块**：**角色 → 任务 → 上下文/约束 → 示例 → 输出格式**。结果不稳定时，**先检查缺了哪个元素，而不是单纯改措辞**。

| 技巧 | 说明 | 适用 |
|---|---|---|
| **System Prompt** | 设定角色、规则、输出格式。优先级最高 | 几乎所有场景 |
| **Few-shot 示例** | **3–5 个**精选示例 | 格式复杂、难以用文字描述清楚时 |
| **思维链（CoT）** | 让模型"先推理再回答" | ⚠️ **原生推理模型上已冗余**（见下） |
| **结构化输出** | 用 JSON Schema 约束输出格式 | 需要程序解析结果时 |
| **明确边界** | 说清楚"不要做什么"，给具体反例 | 防幻觉、防越界 |

**官方原则**：Anthropic 的"**同事测试**"——把 prompt 给一个背景最少的同事看，如果他困惑，模型也会困惑。OpenAI 的说法是"**这些模型读不了你的心**"、"复杂、互相冲突的指令会让模型浪费 token 去解决矛盾"。

#### ⚠️ 2026 年的四个重要变化

**① CoT 已被原生推理内化**

当 extended thinking 可用时，它**通常优于手工 CoT**。官方对推理模型的指导是：**不要做 CoT prompting——模型内部已经在推理**。只需"**写简报，不要写 prompt**"——提供约 **10 倍于预期的上下文**，聚焦 **what 而非 how**。

**② XML 标签与角色扮演从"几乎必选"变为"可选"**

精心设计的 persona 可能**过度约束**现代模型。报道称 Anthropic 为其最新模型**削减了 Claude Code system prompt 的 80% 以上**（⚠️ 厂商自报，未经独立审计）。

**③ Few-shot 在推理模型上可能反噬**

推理调优的模型可能**过度锚定**到你的示例模式，而不再自己找更好的解法。**先尝试删掉示例，再考虑加更多。** 推理模型上 0–2 个示例可能就够了。

**④ 过度详细的指令反而降低质量**

为老模型写的、事无巨细的提示词，迁移到新模型上常常是负优化。原则是：**说清楚目标和约束，而不是规定每一步怎么做**。

#### 结构化输出：三种机制必须分清

| 机制 | 保证什么 | 不保证什么 |
|---|---|---|
| **JSON mode** | 输出是**合法可解析的 JSON** | **不强制任何 schema** |
| **Structured Outputs** ⭐ | 输出**匹配给定 JSON Schema** | — |
| **Function / Tool calling** | 参数符合函数签名 | — |

**底层机制：约束解码（Constrained Decoding）**——生成逐 token 进行，约束引擎插在 **logits 和采样器之间**。每一步把"会破坏 schema 的 token"的 logits 设为 **-∞**，softmax 后概率为 0，因此**"非法输出的失效模式在字面上不可能发生"**。这也是 function calling 底层的同一套机制。

⚠️ **约束解码的两个失效模式**：
1. **过度约束**：如果 enum 里没有正确答案，模型**只能返回一个"错但合法"的值**。→ 加一个"other"逃生舱
2. **隧道视野**：从第一个 token 起就强制 JSON 形状**会损害推理质量**。→ 对复杂任务，**先让模型用自然语言推理，再产出结构化输出**

> **关键认知：结构化输出是采样层的约束，不是质量增强器。**

#### ⚠️ 安全提示

**System prompt 是 prompt injection 的首要攻击面。** Prompt injection 连续第三年位居 **OWASP LLM Top 10 第 1 名**（2026 年 8 月版），其中**通过检索内容的间接注入**被列为更高风险的路径。

### 1.8 上下文工程（Context Engineering）

**Anthropic 于 2025 年 9 月发布工程博客《Effective context engineering for AI agents》，这是该术语获得主流认可的关键节点。**

**官方的定义**：

> **上下文工程 = 在 LLM 推理过程中管理"最优的 token 集合（信息）"，包括所有可能进入上下文的、prompt 之外的信息。**

**与提示工程的区别**：

| | 提示工程 | **上下文工程** |
|---|---|---|
| **关注对象** | 发给模型的**指令文本** | 推理时送达模型的**整个动态系统** |
| **适用场景** | 单轮、边界清晰的任务 | 多轮、累积状态、调用工具、维护记忆的生产级 agent |
| **中心** | **用词（wording）** | **接线（wiring）** |
| **关系** | 是它的**一个子集** | **包含**提示工程 |

**一个关键的量化事实**：在生产级 agent 系统中，**prompt 通常只占上下文窗口的 5–10%**，其余全是它周围的信息架构。

Cognition（Devin 开发商）认为 agent 工程师的**第一要务就是上下文工程**——"prompt engineering 是它更简单的早期版本"。

#### 核心心智模型：上下文是「注意力预算」

> **上下文是 AI 的工作记忆，是一种有限的、边际收益递减的资源。**
> **"随着上下文窗口中 token 数量增加，模型从该上下文中准确召回信息的能力下降。"**

这种 **context rot 是架构性的，而非模型特定的**——根源是 Transformer 的 **O(n²) 注意力：每个新 token 都在与所有已有 token 竞争**。

**黄金法则**：找到**「能最大化期望结果概率的最小高信号 token 集合」**。

#### 通用词汇（2026）

| 分类 | 内容 |
|---|---|
| **四个支柱** | Instructions（指令）、Retrieval（检索）、Memory（记忆）、Tools（工具） |
| **四类失效模式** | Poisoning（投毒）、Distraction（分心）、Confusion（混淆）、Clash（冲突） |
| **四个通用操作** | Write（写）、Select（选）、Compress（压）、Isolate（隔） |

#### 具体战术

**(1) 恰当的「高度」**——避免两个极端：既不要**脆弱的硬编码 if-else**，也不要**含糊的泛泛指导**。目标是不多不少地给出清晰信号（"Goldilocks 区间"）。用 XML / Markdown 分节组织。

**(2) 最小工具集** ⭐——**工具集臃肿、职责重叠是最常见的失效模式之一**。判断标准：**"如果人都分不清该用哪个工具，模型也分不清"**——清晰度胜过覆盖面。

**(3) Few-shot**——精心策展 **3–5 个多样化的典范示例**，而非穷举边缘情况。

**(4) 即时检索（Just-in-time retrieval）** ⭐——不要**预加载**所有数据；让 agent 持有**轻量标识符**（文件路径、查询语句、URL），在运行时按需加载。**Claude Code 就是即时拉取文件，而不是把整个代码库塞进上下文。**

#### 超出单个窗口的三大策略

| 策略 | 说明 | 数据 |
|---|---|---|
| **① 压缩（Compaction）** | 接近上限时摘要对话并重新开始。**工具结果清除是"最安全、最轻量的一刀"**。调优方法：**先最大化召回，再优化精度** | 服务端压缩在 100 轮评估中实现 **84% 的 token 削减** |
| **② 结构化笔记** | 把笔记持久化到**外部记忆**（如 `NOTES.md`），以便在上下文重置后取回 | — |
| **③ 子代理架构** ⭐ **最强手段** | 专门化的子代理做大量探索（数万 token），但**只返回压缩后的 1,000–2,000 token 摘要**。**这是打破上下文天花板最有力的机制** | Anthropic 引用 **90.2% 提升** |

#### ⚠️ 争议与批评

- **"提示工程已死"是夸大其词**——各来源一致认为提示工程**并未过时**，它仍是基线技能，且在 system prompt 和工具描述上**仍然不可或缺**，只是在生产系统中**从属于**上下文工程
- 有论文警告："提示的艺术"叙事**可能掩盖工程债**——把一次漂亮的 demo 误认为生产级方案
- 有评论者认为这次转向**部分是 RAG 的重新包装**
- LangChain 的 Harrison Chase 称上下文工程是"AI 工程师能培养的最重要技能"，但警告**结果仍然是概率性的——"上下文工程没有单元测试"**

> **2026 年的技能含义**：招聘应优先看重**系统思维**——检索管线、记忆系统、状态管理、工具集成——而非提示词雕琢。**这份工作更接近后端系统工程，而非创意写作。**

**为什么这个转变重要**：当模型能力不再是瓶颈时，**喂给它什么信息就成了决定性的变量**。这也解释了为什么同一条经验反复出现：*大多数 Agent 的失败不是推理失败，而是上下文管理失败。*

### 1.9 模型能力分层

**关键前提：三者是同一个预训练骨干的不同"行为版本"，区别在于额外训练的量与类型**，不是三种不同的系统。

```
预训练 → 【基础模型 Base】
       ↓ + SFT（指令-响应对）+ RLHF/DPO 对齐
     【指令微调模型 Instruct】
       ↓ + 强化学习（通常基于可验证奖励）+ 推理 token 训练
     【推理模型 Reasoning】
```

| 维度 | 基础模型 (Base) | 指令微调 (Instruct) | 推理模型 (Reasoning) |
|---|---|---|---|
| **行为** | **"续写文本"，而非回答问题** | 直接作答、遵循指令、多轮对话 | 先"思考"再给答案 |
| **优势** | 原始语言能力、通用性；适合作为**进一步微调的起点** | 遵循指令、直接回答；**更能表达不确定性而非编造** | 多步数学、代码、逻辑、规划、自我检查 |
| **弱点** | **不可靠地遵循指令**，可能跑题或重复 | 同等规模下，极难多步问题上弱于推理模型 | **慢、啰嗦、成本与延迟最高**；简单任务上纯属浪费 |
| **适用** | 自定义微调、语言研究 | **绝大多数日常任务的合理默认值** | **真正需要多步推理的难题**——难、多步、高风险、答案可验证 |

**一个重要研究结论**：推理模型的收益**部分来自更好地导航预训练中已编码的知识**，而不完全是新知识。

**实践工作流**：**默认从快速的指令模型起步；只有当任务确实难、多步、且答案可检查时，才升级到推理模型。**

#### ⚠️ 2026 年的演变：分层正在被「effort 参数」取代

**推理不再是"另一个模型"，而是同一个模型上的一个旋钮。**

- **Anthropic**：`effort` 参数（`low`/`medium`/`high`/`xhigh`/`max`），放在 `output_config` 里。默认 `high`。**`xhigh` 是其编程和 agent 场景的最佳档位，也是 Claude Code 的默认值**
  - 情报敏感工作用 `high` 起步；正确性优先于成本时用 `max`；子代理或简单任务用 `low`
  - **降低 effort 意味着更少、更整合的工具调用，更少前言，更简洁的确认**
- **OpenAI**：`reasoning_effort`（`none`/`minimal`/`low`/`medium`/`high`/`xhigh`，因模型而异）

**成本优化的关键洞察（官方）**：

> 在构建多模型成本级联之前，**先测量更简单的替代方案**——同一个最强模型在**更低 effort** 下的表现。最新模型在低 effort 下往往能匹配甚至超越前代在高 effort 下的表现，而且一个模型意味着一个缓存命名空间（**缓存是按模型隔离的，级联会牺牲跨模型的缓存复用**）。

**⚠️ 评估原则**：按**「完成任务的成本」**判断，而不是按「单次请求的成本」。**一个更便宜但需要更多轮次或重试才能完成的请求，并不便宜。**

### 1.10 ⭐ 最容易被误解的 5 件事（面试高频）

这五条是"看起来对但实际错"的典型。**能在面试里指出它们，比背对十个概念更能体现判断力。**

| # | 常见误解 | 事实 |
|---|---|---|
| 1 | "temperature = 0 就能复现结果" | **错**。浮点运算顺序、批处理、基础设施差异仍带来变动。且**新推理模型根本不接受 temperature** |
| 2 | "上下文窗口 1M 就能可靠处理 1M" | **错**。有效上下文常只有 **30–50%**，且可能在远未填满时**突变式崩溃** |
| 3 | "模型记住了我们的对话" | **错**。API 无状态，每次都在重发全部历史；"记忆"完全是应用层的假象 |
| 4 | "模型变大了所以更真实" | **错**。更大的模型更完整地学到了训练分布，**包括其中的虚假内容** |
| 5 | "提示工程过时了" | **部分错**。它仍是基线技能且不可替代（system prompt、工具描述），只是在生产系统中从属于上下文工程 |

**第 4 条的补充**：幻觉率与规模**不是简单反比**。更大模型在训练分布内更准确，但也会更自信地复现分布中的错误。

## 第 2 部分 · RAG（检索增强生成）

> **你不需要做这个。** 但要知道它是什么、解决什么问题、边界在哪。

### 2.1 是什么

**RAG = 检索增强生成 = 先检索，再生成。**

核心思想（Lewis et al., NeurIPS 2020 原始论文）：把语言模型的**参数化记忆**（模型权重里的知识）与**非参数化记忆**（外部文档索引）结合起来。生成前先从外部语料检索相关段落，再基于这些段落生成答案。

**解决的三个问题**：

| 问题 | RAG 的应对 |
|---|---|
| 模型不知道私有数据 | 外部知识库作为"外挂记忆" |
| 知识过时 | 检索层随时更新，模型权重不动 |
| 幻觉 | 把原文作为"依据"注入上下文 |

⚠️ **但它不能根除幻觉**——这是被反复确认的结论。

### 2.2 完整流程

**离线（索引）**：
```
原始文档 → 解析 → 清洗 → 切分(chunking) → 向量化(embedding) → 入库
```

**在线（推理）**：
```
用户查询
  → (可选) 查询改写
  → 检索（向量 / 关键词 / 混合）
  → (可选) 重排(reranking)
  → 拼装上下文
  → 构造 prompt（含"仅依据上下文"约束）
  → LLM 生成 → 引用溯源 → 返回
```

### 2.3 Embedding：把语义变成几何

把一段文本映射成一串数字（向量，通常几百到几千维）。

**核心性质**：语义相近 → 向量距离近。

所以检索是**语义匹配，不是关键词匹配**。用户说"叶子烂了"也能命中"叶片腐烂"的条目。

- 相似度用**余弦相似度**算（只看方向，不看向量长度）
- **关键约束**：文档和查询**必须用同一个 embedding 模型**，混用会导致向量空间不一致
- 一旦改了切分方式，**必须重算所有 embedding**

### 2.4 切分（Chunking）—— 全流程影响最大的环节

**这是最容易被低估、但影响最大的一步。** 切分失误导致的检索失败，下游任何优化（重排、更好的 prompt）都救不回来。

**为什么必须切分**：
1. Embedding 模型输入长度有限
2. 整篇文档作为一个向量会把多个主题"平均"掉，语义模糊
3. 上下文窗口有限且昂贵
4. 塞得越多，关键信息越容易被淹没

**主流策略**：

| 策略 | 说明 | 适用 |
|---|---|---|
| 固定长度 | 按 token 数切，忽略结构。常用 512~1024 + 10~20% 重叠 | 基线/原型 |
| 递归切分 | 按"段落→句子→词"逐级降级，尽量保留语义边界 | **通用默认推荐** |
| 语义切分 | 相邻句子相似度比较，在话题转移处切 | 计算慢、成本高 |
| 结构感知 | 利用 Markdown 标题、代码函数边界等显式结构 | **结构化数据的最佳选择** |
| 晚切分（Late Chunking） | 先用长上下文模型嵌入整篇，再切分 | 上下文依赖强的长文档 |

**起点建议**：512 tokens。按句子切分被系统研究证实**稳定优于其他启发式方法**。

⚠️ **重叠（overlap）有争议**：主流实践推荐 10-20%，但有系统研究称**重叠没有可测量收益，反而增加索引成本**。把它当需要 A/B 验证的超参，别当无条件默认。

**⭐ 对你有用的**：`pest_database.py` 那种结构化数据（每条记录有明确字段），**按"实体 × 字段"精确切分**比通用切分器准得多。这是可以讲的亮点——大多数人只会用框架的默认切分器。

### 2.5 检索策略

**三种检索方式**：

| | 关键词检索（BM25） | 向量检索 | 混合检索 |
|---|---|---|---|
| 匹配 | 精确词元 | 语义 | 两者融合 |
| 强项 | 稀有词、标识符、编号 | 同义改写、口语查询 | 兼顾 |
| 弱项 | 同义词（"换词就失效"） | 精确标识符 | 需要双索引 |

**融合方法：RRF（Reciprocal Rank Fusion）** 是事实标准。它**只看排名不看原始分数**，绕开了"BM25 分数无界、余弦相似度在 [-1,1]"这种量纲不可比的问题。

⚠️ **混合检索的收益有争议**：乐观派说长尾查询 +15-20% MRR；谨慎派在 WANDS 基准上只测到 +1.7% nDCG。结论：**应该被测量，而不是被假定有益**。

**Top-K 的选择——这里有个反直觉的坑**：

> 把 K 设成 20，然后指望模型"在 20 篇文档里找答案" —— **实测模型主要只看前 3 篇**。这等价于 K=3，同时浪费了约 17 倍的 token。

推荐：起步 K=3；不用重排器则 K≤5；用重排器则粗召回 50 → 精取 5。

**排查规则**（很实用）：
- `hit@3 < 70%` → 问题在**检索器**，不在 K
- `hit@3 > 90% 但答案质量差` → 问题在**生成**，不在 K

### 2.6 重排（Reranking）—— 投入产出比最高的单项优化

**架构**：一阶段检索取 50-200 候选 → 二阶段重排器精排 → 最终 top 5-10

**为什么需要两阶段**：
- 一阶段用的双编码器（bi-encoder）为了能做索引，**必须把查询和文档分开编码**，无法建模两者间的细粒度交互
- 二阶段用交叉编码器（cross-encoder）**把查询和文档拼在一起**过一遍模型，精度最高，但**无法预建索引、延迟高**，所以只对已剪枝的候选集跑

**关键数据**：加任何重排器带来 +6 到 +10 nDCG@10 的提升，而**在重排器之间切换只带来 +2 到 +4**。

**结论**：先按运维约束（能不能自托管、许可、成本）选，不要纠结模型排名。

### 2.7 防幻觉的 Prompt 技巧

**核心模板**：
```
你只能使用下面提供的上下文来回答问题。
如果上下文中找不到答案，就回答"文档中未找到相关信息"。
不要编造文档内容、引文或引用。
所有论断都必须引用具体片段。
```

**几个有效手段**：
- **拒绝回退**：检索为空时直接返回中性声明，**完全避免猜测**
- **引用强制**：提供了上下文却没有引用 → 直接拒绝该回答
- **负向约束 + 反例**："不要猜"、"不确定就说不知道"
- **温度设为 0**（事实检索任务）
- **不要用同一个模型同时做生成器和评判者**

⚠️ **一个重要的负面发现**：基于嵌入相似度和 NLI 的幻觉检测器**不是可靠的安全闸门**——最难检测的幻觉"在语义上与忠实回答无法区分"。推荐用**基于证据做判断的 LLM 推理型评判者**。

### 2.8 RAG 的评测

**必须检索层与生成层分开评**，才能定位故障。

| 层 | 指标 | 看什么 |
|---|---|---|
| 检索 | Recall@K、MRR、nDCG | 该找到的资料有没有被找到 |
| 生成 | Faithfulness、Answer Relevancy | 答案是否忠于上下文、是否回答了问题 |

**诊断矩阵**：

| 症状 | 诊断 | 修复 |
|---|---|---|
| 低 Context Recall | **检索问题**（优先修） | 增大 k、多查询、减小 chunk |
| 低 Context Precision | 检索拉进噪声 | 减小 k、加重排、元数据过滤 |
| 低 Faithfulness | **生成问题** | 降温度、优化 prompt |

⚠️ **重要警示**：2026 年一项元分析用 **20 个框架**评同一批数据，发现**中位相关系数只有 0.21**，92.5% 的样本被判定"有争议"。**当前评测框架测量的不是同一个东西**。所以：不要只信一个框架。

**实践建议**：50 条精心构造的评测集就能给出稳定指标；少于 20 条波动很大。

### 2.9 RAG vs 长上下文 vs 微调

三者**不是竞品**，解决不同问题：

| 手段 | 一句话定位 |
|---|---|
| **RAG** | "模型应该知道**更多会变的事实**" |
| **长上下文** | "模型现在应该**考虑这几份特定文档**" |
| **微调** | "模型应该**表现得不一样**" |

一句被反复引用的总结：**"Fine-tuning is for Form（形式、风格、格式），RAG is for Fact（事实）。"**

⚠️ **长上下文是否让 RAG 过时——这是 2025-2026 最热的争论**：
- 支持 RAG 的证据：LaRA 基准（ICML 2025）结论是"没有普适赢家"；Lost in the Middle 问题持续存在；超过某规模阈值后 RAG 仍不可替代
- 反对的声音：小规模语料（<100K token）转向"长上下文优先"
- **当前主流实践是折中**：自适应路由 + 混合架构（先检索召回 30K，再放进长窗口深度推理）

**实操决策**：数据 >1M token 或高频变化 → RAG；<500K 且稳定 → 先试长上下文；原型阶段 → RAG 优先（1-3 天可上线）。

## 第 3 部分 · Agent

### 3.1 定义：一句话区分

> **LLM 调用是"问一次答一次"；Agent 是"为了达成目标而在循环中调用工具"。**

Simon Willison 的定义被广泛引用：agent 是 *"something that runs tools in a loop to achieve a goal"*。

### 3.2 ⭐ 最重要的一组区分：Workflow vs Agent

这是 Anthropic《Building Effective Agents》提出的、至今仍是行业标准的概念区分：

| | 定义 | 谁掌握控制流 |
|---|---|---|
| **Workflow 工作流** | LLM 和工具通过**预定义的代码路径**被编排 | **你**（开发者） |
| **Agent 智能体** | LLM **动态决定**自己的流程和工具使用 | **模型** |

**判定标准（一句话）**：
> *"看下一步是由模型根据观察结果决定的，还是硬编码的。如果是硬编码的，你有的只是一个工作流。"*

**这个概念为什么对你特别重要**：因为你**大概率应该用 Workflow**。业界一致建议是"大多数任务应该用 workflow，不是 agent"。

### 3.3 ReAct 循环

ReAct（Reasoning + Acting, 2022）是绝大多数 agent 的底层范式：

```
1. 目标/观察   ← 接收目标与规则
2. 推理/规划   ← 模型决定下一步（由 AI 推理得出，不是人预先定义）
3. 行动        ← 调用工具：查库、跑代码、读文件、调 API
4. 观察        ← 捕获环境真实返回
5. 反思/纠正   ← 目标达成？否 → 调整后回到第 2 步
```

技术上就是：每次迭代做一次 LLM 调用决定下一个动作 → 选到工具就执行 → 把结果注入 → 重复直到结束。

### 3.4 ⭐ 可靠性数学：为什么"多步"是危险的

**这是最被忽视、但最重要的工程直觉。**

因为每步成功是**相乘**的（n 步成功率 ≈ pⁿ）：

| 单步成功率 | 10 步 | 20 步 |
|---|---|---|
| 95% | ~60% | ~36% |
| 90% | ~35% | ~12% |
| 85% | ~20% | ~4% |

多智能体更糟：10 个 agent 各 95%，端到端只有约 **59.8%**。

**工程含义**：
- **链条要短**
- **步与步之间要验证**
- **不可逆操作要人审**
- **循环要有步数和成本上限**——"让一个困惑的 agent 便宜地失败，而不是昂贵地失败"

> 一个真实案例：某 agent 在 5 分钟内调用了一个坏掉的工具 **400 次**。

### 3.5 上下文管理：Agent 真正的难点

**2026 年的核心论点：大多数 Agent 失败不是推理失败，而是上下文管理失败。**

**短期 vs 长期记忆**：

| | 短期记忆 | 长期记忆 |
|---|---|---|
| 载体 | 上下文窗口内 | 外部存储（文件、向量库、DB） |
| 风险 | 溢出、噪声 | 过期、矛盾、错误固化 |
| 操作 | 检索/摘要/过滤 | 增/改/删 |

**成本结构**（很重要）：
- 朴素累积上下文 → token 成本**二次增长**
- 粗暴摘要 → 线性成本，但**准确率断崖**
- 只有**经过验证的压缩**才能同时做到线性成本和保真

**压缩（Compaction）的设计原则**（学术共识）：
1. 压缩是**协议的一部分**，不是补救动作
2. 用户内容不可侵犯
3. **因果依赖优先于时间新近性**
4. **压缩过程尽量不要调用模型**——从结构上避免"压缩导致的幻觉"
5. 淘汰要**渐进**，不要灾难式

### 3.6 ⚠️ 反思与自我纠错：厂商宣传与实证落差最大的一节

**主流做法**：Reflexion、Self-Refine——让模型批评自己的输出再改进。

**但实证证据相当负面**：

| 发现 | 含义 |
|---|---|
| 多轮自我反馈循环**可能伤害而非帮助**推理任务 | ICLR 2024/2025 论文 |
| 约 **70%** 的推理错误源于"验证"环节 | 验证才是瓶颈，不是反思本身 |
| **"自批评悖论"**：简单任务上批评会**发明错误**（准确率 98.1% → 56.9%）；困难任务上才显著提升 | Snorkel AI |
| 开放式任务中，反思后 **80.8% 的失败是同类重复** | "反思并不把解释转化为纠正" |
| **记忆固化**：32% 的环境出现反思内容近乎重复；16 个固化环境中 121 条反思里 **0 条**提到正确目标 | "记忆虚构" |

**✅ 结论**：被提示词驱动的自我纠错**不是免费午餐**。只有在**困难任务 + 错误可观测 + 有外部信号锚定**时才真正有效。

**正确做法**：
- 把纠错**锚定在外部信号**上（工具返回值、测试结果），而不是模型自我判断
- 让验证**模块化且轻量**（验证可以比生成便宜）
- 加**动态回退**机制：重复同一个失败修正时，放宽约束或回滚

> **批判性判断**："self-healing agent""自反思 agent"是常见的营销词。判断一个 agent 产品好坏，**看它有没有独立于生成器的验证器**，而不是看它有没有"反思"。

### 3.7 工具使用（Function Calling）机制

**核心原理**：**模型永远不执行你的代码。** 它返回一个结构化的"调用请求"，由**你的应用**执行真正的逻辑。

**完整循环**：
1. 在请求里提供工具定义（名称、描述、参数 JSON Schema）
2. 模型判断是否需要调用
3. 模型返回结构化调用（不是自然语言文本）
4. **你的应用执行**——注意参数是 **JSON 编码的字符串**，不是已解析对象
5. 把结果回填给模型
6. 模型生成最终回答，或再次调用工具 → 循环

**工具设计的要点**：
- 一开始可用工具数量**保持在 20 个以内**
- 用 enum 和对象结构**防止非法状态**（反例：`toggle_light(on: bool, off: bool)` 允许非法调用）
- 应用"**实习生测试**"：一个聪明实习生能只凭描述正确使用吗？
- 工具描述会被注入 system prompt，**计入 context 且按 input token 计费**

**常见工程坑**：
- 把参数当对象用（它其实是字符串）
- 工具结果太啰嗦：5-8 次调用可能吃掉窗口的 30-50%
- **工具执行失败时没有把错误回传给模型**，导致模型编造答案

### 3.8 什么任务适合 Agent

**Anthropic 的四个判断问题**：

1. **任务是否足够模糊，以至于你无法预先画出决策树？** 能画出来 → 建 workflow
2. **任务价值是否高到值得花 token？** Agent 会探索，探索要花钱
3. **瓶颈能力是否扎实？** 否则错误会在每轮循环中累积
4. **犯错的代价是多少？** 高风险、难检测的错误会让自主性变成负债

**适合 Workflow**：能画出决策树、路径有限、逻辑确定性、严格延迟/成本边界、需要完全可复现和审计。
**适合 Agent**：开放式、模糊、路径事先不清楚、运行时"选哪个工具"本身就是价值。

> **关键洞察**：**可验证性是 Agent 能力的边界。** LLM 能自动化的，是你能验证的东西——能力在数学和代码这类可验证领域达到峰值。

**编程被公认为 Agent 的强适配场景**——因为它同时满足上面四条。

### 3.9 常见失败模式

| 失败模式 | 说明 |
|---|---|
| 工具调用错误 | 参数格式错误、选错工具、忽略失败后编造答案 |
| **静默失败** | 不完整上下文被传递，**不抛错**，监控一片绿 |
| **幻觉级联** | 第 2 步的一次编造污染所有下游，且**看不到起源** |
| **推理循环** | 实测：112 次运行中 **84 次（75%）**耗尽迭代上限 |
| 上下文爆炸 | 循环的 agent 一夜烧掉几千美元 |

> **只用标准 OpenTelemetry 追踪，你能看见不到一半的 Agent 故障。**（实测故障检出率 0.429 vs 完整方案 1.000）

### 3.10 多智能体（Multi-Agent）：一个真实的技术辩论

**这不是"最佳实践"，是有分歧的领域。**

| 立场 | 代表 | 论点 |
|---|---|---|
| **反方** | Cognition《Don't Build Multi-Agents》 | 多数团队因习惯或炒作选择多智能体。设计良好的**单** agent 表现更好、灾难性失败更少。多 agent 引入通信边界 → "context catastrophe" |
| **正方** | Anthropic | 多智能体研究系统性能高 90.2%；**但自己也承认**消耗 3-10 倍 token，且**不适合需要共享上下文的任务** |

**辩论的实质**：双方立场不矛盾，而是划分了适用边界——

| | 适合单 Agent | 适合多 Agent |
|---|---|---|
| 任务依赖度 | 高依赖、紧耦合（如编程） | 低依赖、可并行 |
| 典型场景 | 代码修改 | 研究、信息搜集 |
| 成本容忍度 | 低 | 高（3-15 倍 token） |

**有价值的细节**：任务分解应遵循**上下文/领域边界**，而不是**项目阶段**。按阶段分解（先设计、再实现、再测试）会造成交接时的上下文丢失。

**✅ 结论**：默认从单 agent 开始。多智能体只在"上下文污染确实在损害性能 + 工作确实可并行"时使用。警惕"**披着聊天机器人外衣的 if-else 流水线**"。

### 3.11 ⚠️ 基准测试的严重问题（面试时必知的批判视角）

**如果你在面试里引用 "SWE-bench 95%" 这类数字，可能会被追问到崩。**

| 问题 | 证据 |
|---|---|
| **可被作弊** | Berkeley RDI 证明 **8 个主流 agent benchmark 全部可被 reward hack 到接近 100%**——一个 exploit agent 在**完全没有解决任何任务**的情况下获得近满分 |
| **脚手架敏感** | 同一模型在不同 scaffold 下得分能差 **10-30 分** |
| **污染** | 训练过开源代码的模型很可能见过 benchmark 仓库 |
| **测试缺陷** | 一项审计发现 benchmark 中**至少 59.4% 的问题存在有缺陷的测试用例**，会拒绝功能正确的解法 |
| **范围狭窄** | 有界沙箱剥离了歧义，奖励单次完成——不是真实的多服务 bug |
| **基准到生产的鸿沟** | 约 **37%**。一个 SWE-bench 93.9% 的模型，生产中可能只交付约 60% 的可靠性 |

**✅ 实用结论**：公开 benchmark 适合**粗筛模型和追踪领域进展**，**不是生产部署标准**。

## 第 4 部分 · MCP（Model Context Protocol）

> 同样：**你不需要做这个**，但要知道它是什么。

### 4.1 解决什么问题

**MCP 是一个开放协议，让 LLM 应用与外部数据源和工具无缝集成。** 灵感来自 **LSP（Language Server Protocol）**——正如 LSP 标准化了编辑器与语言的集成。

**核心价值：把 N×M 问题降维成 N+M。**

原本：每个模型 × 每个工具都要写定制适配器。
现在：工具写一个 MCP server，模型写一个 MCP client，两者互通。

### 4.2 架构：Host / Client / Server

基于 **JSON-RPC 2.0**：

| 角色 | 职责 |
|---|---|
| **Host 宿主** | 发起连接的 LLM 应用（如 Claude Code）。管理多个 client、控制权限、执行安全策略 |
| **Client 客户端** | Host 内的连接器，**每个维持一个隔离的 server 连接** |
| **Server 服务端** | 提供能力：**Resources**（上下文数据）、**Prompts**（提示模板）、**Tools**（可执行函数） |

**设计原则**：Server **不应能读取整个对话**，也不应能"看进"其他 server；完整对话历史留在 host。

### 4.3 ⚠️ 重要变化：从有状态到无状态

| 规范版本 | 连接模型 |
|---|---|
| 2024-11-05 | 有状态 |
| 2025-11-25 | 有状态会话 |
| **2026-07-28** | **无状态、自包含请求 + 每请求能力协商** |

2026-07-28 版是一个**重大架构转向**——对水平扩展和部署形态影响很大。

### 4.4 为什么重要：治理

**2025 年 12 月，Anthropic 把 MCP 捐赠给了 Agentic AI Foundation（AAIF）**——Linux Foundation 下的定向基金。联合创始方为 **Anthropic、Block、OpenAI**，支持方包括 Google、Microsoft、AWS、Cloudflare。

到 2026 年 4 月，AAIF 成员已超过 170 家组织。这使 MCP 实现**厂商中立、社区治理**，显著降低了企业的采用风险。

### 4.5 ⚠️ 批评与安全

**安全**（官方文档也承认）：
- MCP 带来**任意数据访问和代码执行路径**
- 已发布严重 CVE：**CVE-2025-49596（CVSS 9.4）**、**CVE-2025-6514（CVSS 9.6）**
- **53% 的集成仍使用静态 API key**
- 工具注解（annotations）应视为**不可信**，除非来自可信 server

**有争议的声音**：
- Perplexity 于 2026 年 3 月宣布**内部放弃 MCP**
- Google Workspace 在 v0.8.0 **悄然移除了 MCP 支持**
- 核心批评：**"MCP 搬运上下文，但不生产也不治理上下文。"**

> **批判性判断**：MCP 的标准地位基本确立（三大实验室 + 微软全部支持），但**"MCP 解决了 agent 数据问题"是夸大宣传**——它解决的是**接口标准化**，不是**数据可信度**。

## 第 5 部分 · AI 辅助软件开发 ★

> **这是你岗位的核心，也是这份材料最重要的一部分。**

### 5.1 工具形态：四类分工

业界已形成四类工具，**没有任何单一工具覆盖全部**：

| 类别 | 代表 | 交互模式 |
|---|---|---|
| **IDE 原生（你驾驶）** | Cursor、Windsurf、Copilot Agent、JetBrains AI | 编辑器内，你主导 |
| **CLI / 终端 Agent** | **Claude Code**、Codex CLI、Aider、Gemini CLI、Cline | 终端原生 |
| **云端长时 Agent（派活走人）** | **Devin**、Codex Cloud、Copilot Coding Agent | 派任务后离开 |
| **PR 审查专家** | CodeRabbit、Greptile、Cursor Bugbot | 审查门禁 |

**选型原则（比排行榜有用）**：
- 按**控制模型**选，不按排行榜选：PR 审查 → Copilot/Codex；深层单体重构 → Claude Code；采购摩擦 → Aider/Cline
- 用量不可预测时，优先**固定座位定价**而非按量计费
- 注意**厂商连续性**：Windsurf、Supermaven、Continue.dev 都因收购改变了状态

**采用度背景**：Stack Overflow 2025 显示 **84%** 开发者使用或计划使用 AI 工具，但 **46% 主动不信任其准确性**。这决定了你应该选择"**怀疑者真的会去读的审查界面**（diff、日志、checkpoint）"。

### 5.2 ⭐ 核心工作流：Explore → Plan → Code → Commit

Anthropic 官方推荐的工作流：

1. **Explore（探索）**——让 agent 在提出改动**之前**先读相关文件和依赖
2. **Plan（规划）**——要求写出一份计划（动哪些文件、方法、顺序）。**审查并纠正它**
3. **Implement（实现）**——批准计划后执行
4. **Commit（提交）**——验证后提交，附清晰消息

> **一句话 diff 可以跳过这套仪式；任何你会认真审查的改动都应该用。**

**为什么 Plan 这一步价值极高**：
> **修计划很便宜，修 600 行错代码不便宜。**

**Plan Mode** 是一个**系统级的意图闸门**：在你批准前，**物理上阻止** agent 写代码。适用于多文件改动、架构决策、危险操作。

### 5.3 规格先行（Spec-Driven Development）

GitHub **Spec Kit** 是规格驱动开发的参考实现，驱动多种编码 agent。

**核心流程**：`Specify → Plan → Tasks → Implement → Converge`

**核心原则**：
- **规格是真相来源，不是代码**。代码是规格的产物
- **只写 WHAT 和 WHY，不写 HOW**。实现细节属于 plan 阶段
- **小、有序、可测试的任务**
- **constitution（章程）阶段**是团队最常遗漏、也最重要的——它把仓库的隐式约束（风格、架构、"别破坏 X"）从审查者脑子里搬到 agent 首先阅读的文档中

⚠️ **验证纪律（关键）**：
> **"每个检查点的验证不能委派给产出它的 agent。"**

⚠️ **官方承认的局限**：Spec Kit **不能**修正错误的 spec、不保证实现正确性、不交付安全性。长时间实现会随着窗口填满而丢失计划上下文。

⚠️ **过度规格化是一种真实失败模式**——"审查成本超过它所治理的改动"。对一次性原型、微小修复，完整流程通常过重。

### 5.4 Karpathy 的 "Agentic Engineering"（2026 年 2 月提出）

作为 "vibe coding"（他 2025 年 2 月命名）的专业继任者：

| 维度 | Vibe Coding | **Agentic Engineering** |
|---|---|---|
| 核心模型 | "描述并接受" | **"编排并监督"** |
| 谁写代码 | AI 生成，人接受 | AI 生成，人**以审查人类 PR 的同等严格度**审查 |
| 规划 | 立即开始提示 | **提示前先规划**——spec、设计文档 |
| 测试 | 希望它能跑 | **不厌其烦地测试**（最大区分点） |
| 适用 | 原型、探索 | **生产系统、团队项目** |

**两句话**：
> "**Vibe coding 抬高了所有人的下限。Agentic engineering 是在不降低质量门槛的前提下走得远快得多的纪律。**"
> "**你不被允许因为 vibe coding 而引入漏洞。**"

**五个关键要素**：① 规格先行 ② 人类审批闸门 ③ 隔离执行环境 ④ **可验证的验收标准**（不是"看起来对"，而是"通过测试、满足 spec"）⑤ PR 审查循环。

**其他重要观点**：
- **可验证性**：LLM 自动化的是你能验证的东西
- **锯齿状智能（jagged intelligence）**：模型能重构 10 万行代码库，却在简单常识任务上失败——所以人必须留在循环里
- **"注意力"才是真正的收益**：关键不是总时间节省，而是**释放的注意力**

### 5.5 ⭐ 给 AI 提供上下文：CLAUDE.md / AGENTS.md

**这是你 A 类岗位的招牌，也是最容易做砸的地方。**

**两者的定位**：

| | AGENTS.md | CLAUDE.md |
|---|---|---|
| 范围 | **跨工具**（20-30+ agent） | 仅 Claude Code |
| 治理 | Linux Foundation 下的 AAIF，**60,000+ 项目**采用 | 厂商自有 |
| 格式 | 纯 Markdown，无必需字段 | Markdown + `@imports` |
| 大小 | Codex 默认 **32 KiB 上限，超出静默截断** | 建议 200 行以内 |

**✅ 多工具项目的推荐拓扑**：把 `AGENTS.md` 作为唯一真相来源，让 `CLAUDE.md` 只包含一行导入：
```
@AGENTS.md
```
**不要**在多个文件里维护同一套规则的副本——它们会漂移并互相矛盾（一个说 Java 17，另一个说 Java 8）。

#### 编写最佳实践

**要短**：目标 200 行以内。**更短的文件表现更好**，因为每一行都在争夺 agent 的上下文预算。

**写命令，不写散文**：
> ✅ "Run `pnpm test`" 胜过 ❌ "we have a comprehensive testing strategy"

Agent 会执行前者，并真的会在宣称任务完成前跑列出的测试命令。

**要包含**只有非显然的、项目特有的信息：
- 精确的 setup/build/test 命令及参数
- 与默认不同的规则
- 架构约束、明确的边界
- 项目特有的坑

**要排除** agent 自己能找到的东西：标准约定（PEP 8、Prettier 默认值）、`package.json` 里已有的命令、完整 API 文档、显而易见的建议（"写干净的代码"）。

#### ⚠️ 一个反直觉但有实证的发现

> 🔬 研究：**LLM 生成的 AGENTS.md 文件略微降低了任务成功率，同时增加了 23% 的成本**；**人类编写的文件把成功率提升了约 4%**。

**写得好的文件有帮助，冗余的自动生成文件有伤害。** 这直接印证了本材料的主线——**你的价值在于判断力，不在于让 AI 多产出**。

#### 🔬 实测收益

Princeton 研究在 10 个仓库、124 个已合并 PR 上对比有/无 AGENTS.md：
- **中位运行时间减少 28.6%**（98.6s → 70.3s）
- **中位 token 减少 16.6%**

⚠️ 局限：只覆盖小 PR（100 行以内、≤5 文件）。

#### ⚠️ 指令 ≠ 安全控制

> **"never commit secrets" 是一句提醒，不是保证。**

硬性限制要用**权限、密钥扫描、hooks、测试或 CI** 来强制。

### 5.6 ⭐ AI 生成代码的质量控制

**核心原则**：
> **把 AI 生成的代码当作未验证的输入，而不是可信的输出。**

**具体机制**：

1. **测试是黄金标准（外部 oracle）**
   - "让这个测试通过"是 agent 能自我闭合的最强循环
   - 推荐 TDD：先写测试 → 确认失败 → 提交失败测试为检查点 → 实现直到变绿
   - 用一个 subagent 验证实现**没有过拟合到测试**

2. **客观信号**：构建/类型检查的退出码；UI 工作的截图

3. **Hooks 作为确定性闸门**（关键数据）：
   > **CLAUDE.md 指令的遵循率约 80%，而 hook 是 100%。**
   - **Stop hook** 可以跑测试套件，以 exit code 阻塞并反馈失败
   - **PreToolUse hook** 可以阻止提交
   - **PostToolUse hook** 在编辑后自动格式化/类型检查

4. **独立上下文的对抗性审查**
   > ✅ 关键洞察：**在同一个会话里审查自己工作的 agent，会偏向于它自己。**
   
   要有独立上下文、任务是**反驳改动或找 bug** 的 subagent。

5. **CI/CD 门禁**：SAST/SCA 作为必备门禁；**验证 AI 建议的包是否真实存在**；按风险分层人工审查（认证、API 边界、数据持久化、加密）

**被反复强调的一句话**：
> **"质量来自外部机制，而不是 AI 的自我判断。"**

### 5.7 常见陷阱

#### 幻觉 API 与"抢注包"（slopsquatting）

LLM 编码助手会产生"**自信但错误**"的输出——**假 API、无效参数、不存在的库**。

🔬 **不只是烦人**：编造的包名可以被 **"slopsquatting"** 利用——**攻击者注册 AI 建议的假包名以实施供应链攻击**。

其他：**不安全模式继承**（复现训练数据中的历史 bug）、**提示注入**（藏在注释或文档中）。

#### 过度生成 / 抽象膨胀

- Agent 会**过度工程**并留下垃圾代码
- 🔬 "生产率-质量悖论"研究：**代码重复增加 4 倍、代码 churn 翻倍**

#### 三种新失败模式（Addy Osmani《The 80% Problem》）

1. **假设传播（assumption propagation）**——一个早期错误假设被放大到许多特性上
2. **抽象膨胀**——agent 过度工程并留下残留
3. **谄媚式同意（sycophantic agreement）**——agent 对不清晰或矛盾的需求**不提出异议，直接执行**

> ⚠️ 诚实评价：一份资源评估给 Osmani 这篇文章打 3/5，指出它是二手综合、若干统计数字无法验证。**但"80% problem"框架和三种失败模式分类仍是有用的**。

#### ⭐ 理解债务（Comprehension Debt）—— 对你最重要的一条

| 术语 | 定义 |
|---|---|
| **认知债务** | "AI 辅助生产能力与人类理解能力之间累积的失衡" |
| **理解债务** | 生成代码与人类对它的理解之间日益扩大的鸿沟 |

> **如果你的"阅读"能力跟不上 agent 的"输出"能力，你不是在做工程，你在盖章（rubber-stamping）。**

**其他相关债务**：快速集成债（快速实现 AI 建议而不理解含义）、prompt debt、agentic debt。

🔬 **相关数据**：
- 上线的代码中 AI 生成缺陷率：IDC 称 **70% 使用 GenAI 的开发者必须修复多达 40% 的生成代码**（⚠️ 二手引用）
- **44%** 的开发者手写代码不到 10%
- PR 数 **+98%**，审查时间 **+91%**
- 只有 **48%** 的开发者系统性地审查 AI 代码
- **99%** 报告节省 10+ 小时，但**工作量没有减少**

#### 🔬 安全与过度依赖

- **不到 25%** 的开发者对 AI 生成代码使用软件成分分析（SCA）
- **约 80%** 承认在 AI 辅助工作流中绕过安全策略
- 核心论断：**生产可用代码的门槛降低了，但评估它的门槛（尤其安全）没有降低**

#### ⚠️ 底层机制

🔬 研究把 LLM 描述为"**一堆启发式和捷径**"的集合——当任务与训练数据对齐时有效，但**无法泛化**——并且它们"**不提供任何客观的置信度度量**"，以不应有的确定性呈现输出。

### 5.8 ⭐⭐ 实证数据：AI 到底有没有提效

**这一节直接关系到你的面试策略，请认真读。**

#### METR 随机对照试验（RCT）

**这是本领域方法学最扎实的研究**：
- **16 名**经验丰富的开源开发者
- **246 个**来自他们日常工作的真实任务，切成 1-2 小时的小块
- 参与者贡献的项目平均超过**一百万行代码**
- 任务**随机分配**到"允许 AI"或"禁止 AI"条件
- 开发者**事先不知道**自己是否能用 AI

**关键发现**：
- 使用 AI 的开发者完成任务**慢了 19%**（置信区间 +2% 到 +39%）
- 这与预期**直接矛盾**：开发者自己预测会快 **24%**
- **感知落差**：即使看过自己的计时数据和录屏后，开发者**仍然相信** AI 让他们快了约 20%——**约 39 个百分点的落差**

**为什么资深开发者变慢了**：
- **心流中断**——有强心智模型的开发者不得不阅读、审查、并常常纠正 AI 输出
- **75%** 逐行阅读 AI 输出；**56%** 做了重大修改；**最终接受率低于 44%**
- **AI 在专业度低的地方帮助最大**（不熟悉的代码库、样板代码），**在专业度高时反而碍事**

**⚠️ 后续研究的诚实说明**：METR 做了第二次研究（更大样本），但判定数据**"不可靠"**——因为 **30-50% 的开发者跳过了任务提交**（他们不想在没有 AI 的情况下工作），许多开发者拒绝参与。这些选择效应**系统性地移除了最狂热的 AI 采用者**。新的估计是 -18%（快 18%），但**置信区间跨过零轴**，METR 称之为"非常弱的证据"。

> **核心悖论**：**AI 越成功，就越难测量它的影响。** RCT 需要一个不用 AI 的对照组——但随着开发者依赖 AI，这个对照组正变得**不可能招募**。

#### DORA 2025《State of AI-assisted Software Development》

基于近 **5,000 名**技术专业人士：

**核心主题**：**AI 不修复团队，它放大既有状况。**

**关键数据（最重要的一组）**：
- AI 加速开发，但**加速暴露了下游弱点**
- **AI 采用度增加 25%** 与**交付吞吐量下降 1.5%** 和**交付稳定性下降 7.2%** 相关（早期研究）
- 2025 年报告观察到吞吐量正相关，但**稳定性仍持续负相关**
- **解释**：没有健壮的自动化测试、成熟版本控制和快速反馈循环，变更量增加会导致不稳定。**松耦合架构 + 快速反馈的团队看到收益；紧耦合、慢流程的团队几乎看不到好处**

**信任悖论**：尽管采用度高，**30%** 报告对 AI 生成代码**很少或没有信任**；信任度从 2024 年的 87.9% 跌到 2025 年的 70%。

#### Stack Overflow 2025 开发者调查（约 49,009 份回应）

| 指标 | 2025 | 2024 |
|---|---|---|
| 使用或计划使用 AI 工具 | **84%** | 76% |
| **不信任** AI 输出准确性 | **46%** | 31% |
| "高度信任" | **3%** | — |

**经验越丰富越谨慎**：**75.3%** 说他们不信任 AI 答案、宁愿问同事；**61.3%** 想要完全自己理解代码；**45%** 觉得调试 AI 生成代码耗时。

#### ✅ 综合解读

| 结论 | 判断 |
|---|---|
| AI 工具采用率极高（84-90%） | ✅ 共识 |
| 开发者**自感**效率提升 | ✅ 但**感知不可靠** |
| **客观**生产率提升 | ⚠️ 弱/矛盾 |
| AI 提高交付吞吐量 | ⚠️ 中等，且有代价 |
| AI **降低**交付稳定性 | 🔬 较强 |
| 信任度**在下降** | 🔬 强 |

> **最重要的元结论**：**"开发者感觉自己更快了"与"开发者实际更快了"之间存在高达 39 个百分点的落差。**

### 5.9 ⭐ 这些数据对你的面试意味着什么

**不要说**（会被追问到崩）：
- ❌ "我用 AI 提效了 3 倍"——自报数据不可信，且面试官可能知道 METR
- ❌ "AI 生成的代码我基本不用改"——与实证数据严重矛盾
- ❌ "我让 agent 自己反思纠错就行了"——没有外部验证器的自反思基本不可靠

**要说**（这些是加分项）：
- ✅ "我用 AI 做**我有判断力**的部分——样板代码、不熟悉的 API、测试脚手架"
- ✅ "**关键路径我自己写**，因为那是我心流最强、AI 反而拖慢的地方"
- ✅ "我靠**外部机制**保证质量：测试、类型检查、hooks、独立上下文的审查"
- ✅ "我注意过**理解债务**的问题——如果我不理解 AI 写的代码，我就不会提交"
- ✅ "我意识到**感知效率提升和实际效率提升是两件事**，所以我会看实际指标"

**最有力的回答**：把"39 个百分点落差"这个事实讲出来，说明你**知道 AI 提效的边界在哪**。这体现的是判断力，正是 A 类岗位最稀缺的东西。

## 第 6 部分 · 术语速查表

按出现顺序排列。

#### 第 1 部分（LLM 基础）

| 术语 | 一句话 |
|---|---|
| **自回归生成** | 把自己的输出接回输入，逐个 token 生成 |
| **BPE（字节对编码）** | 主流分词算法：反复合并最高频的相邻 pair，直到词表达标 |
| **Token** | 介于字符与词之间的子词单位。**计价和容量的基本单位** |
| **parity ratio** | 某语言每字符 token 数 ÷ 英文。衡量 tokenizer 的跨语言公平性 |
| **上下文窗口** | 模型一次能看到的 token 上限。是"工作记忆"不是"长期记忆" |
| **Context Rot（上下文腐化）** | 性能随输入变长而**持续下降，远在窗口填满之前就开始** |
| **Lost in the Middle** | 关键信息在长上下文中部时被忽略，形成 U 型性能曲线 |
| **temperature** | 采样随机性。⚠️ **2026 年推理模型已移除该参数，改用 effort** |
| **top_p** | 从累积概率前 p% 的词里采样。比 temperature 更自适应 |
| **幻觉** | next-token prediction 的必然副产品——优化"听起来对"而非"是真的" |
| **语境不忠** | 检索到了正确信息，却未能把生成锚定于该信息 |
| **无状态性** | API 不记忆，每轮必须重发全部历史 |
| **Prompt Caching** | 相同前缀命中缓存，读取价约 10%。**前缀改一个字节就全失效** |
| **keepalive** | 暂停期间定时重发相同前缀，防止缓存 TTL 过期 |
| **上下文工程** | 管理推理时送达模型的**整个动态系统**（提示工程的超集） |
| **注意力预算** | 把上下文看成有限资源，每个新 token 都在竞争注意力 |
| **effort** | 控制推理模型的思考深度与 token 花费（`low`→`max`） |
| **约束解码** | 在采样层把非法 token 的 logits 设为 -∞，使非法输出"字面上不可能" |

#### 第 2–4 部分（RAG / Agent / MCP）

| 术语 | 一句话 |
|---|---|
| **Embedding** | 把文本映射为向量，语义相近则距离近 |
| **Chunking** | 文档切分。**RAG 中影响最大的环节** |
| **Reranking** | 两阶段检索的精排环节，**投入产出比最高的单项优化** |
| **RAG** | 检索增强生成：先检索，再生成 |
| **Function Calling** | 模型输出结构化调用请求，**由应用执行**（模型永不执行你的代码） |
| **ReAct** | 推理-行动循环，Agent 的底层范式 |
| **Agent** | LLM 在循环中调用工具以达成目标 |
| **Workflow** | LLM 和工具按**预定义代码路径**编排，**控制权在你** |
| **MCP** | 标准化"模型连接工具"的开放协议，把 N×M 降为 N+M |
| **Compaction** | 上下文压缩。**是协议的一部分，不是补救动作** |
| **pⁿ 可靠性衰减** | n 步任务的成功率 ≈ 单步成功率的 n 次方。**链条越长越危险** |

#### 第 5 部分（AI 辅助软件开发）

| 术语 | 一句话 |
|---|---|
| **Oracle** | 外部验证依据（测试、类型检查）。**质量来自外部机制** |
| **Spec-driven development** | 规格先行：**规格是真相来源，不是代码** |
| **AGENTS.md / CLAUDE.md** | 给 agent 的项目上下文文件。**写命令不写散文，200 行以内** |
| **理解债务** | 生成代码与人类理解之间的鸿沟。**跟不上就是在盖章** |
| **Agentic Engineering** | 编排并监督 AI 写代码，**以审查人类 PR 的同等严格度**审查 |
| **slopsquatting** | 攻击者注册 AI 幻觉出的假包名，实施供应链攻击 |
| **假设传播** | 一个早期错误假设被放大到许多特性上 |
| **谄媚式同意** | agent 对不清晰或矛盾的需求**不提出异议，直接执行** |

## 附录 A · 模型与 API 关键数据

> 数据来源：官方参考，缓存于 2026-06-24。**使用前请核对官方最新文档**。

### 主流模型（Claude 家族）

| 模型 | Model ID | 上下文 | 输入 $/1M | 输出 $/1M |
|---|---|---|---|---|
| Claude Fable 5.1 | `claude-fable-5-1` | 1M | $10.00 | $50.00 |
| Claude Opus 5 | `claude-opus-5` | 1M | $5.00 | $25.00 |
| Claude Opus 4.8 | `claude-opus-4-8` | 1M | $5.00 | $25.00 |
| Claude Sonnet 5 | `claude-sonnet-5` | 1M | $2.00 | $10.00 |
| Claude Haiku 4.5 | `claude-haiku-4-5` | 200K | $1.00 | $5.00 |

**几个要点**：

- **上下文窗口 1M 已是中端标配**（Haiku 除外），所有较大模型的最大输出为 128K
- 输出价格通常是输入的 **5 倍**
- 模型 ID **不要加日期后缀**（`claude-opus-5`，不是 `claude-opus-5-20260401`）
- 具体能力/窗口用 Models API 实时查询，**不要凭记忆**
- **Mythos 5 / 5.1** 与 Fable 同权重、能力/价格/API 完全一致，但**仅面向 Project Glasswing 批准客户**（更少护栏）
- **Fable 5** 是当前最强大的公开发布模型：**思考始终开启**（无法关闭）、**不接受采样参数**、**无 assistant prefill**

#### ⚠️ 三个会直接导致报错的迁移断点

| 断点 | 说明 |
|---|---|
| **采样参数被移除** | `temperature` / `top_p` / `top_k` 在 Opus 4.7+ / Sonnet 5+ 上**传入即 400**。官方指导是**完全省略**，而不是设默认值或 null |
| **assistant prefill 被移除** | Claude Opus 5 / Sonnet 5 / Fable 5 及 4.6+ 家族**传 prefill 会 400** |
| **tokenizer 变更** | Opus 4.7 的 tokenizer 是 1×–1.35×；Sonnet 4.6 → Sonnet 5 **相同文本约多 30% token**。**迁移时必须重新基线化 token 计数和成本预估** |

#### 一个容易漏掉的 stop reason

⚠️ **`refusal` 是一个独立的 stop reason**——HTTP 200 但 `stop_reason: "refusal"`。**读取 `content` 前必须先检查 `stop_reason`**，否则会把拒答内容当正常输出处理。官方建议默认启用服务端 `fallbacks` 参数。

### 关键机制速查

**Thinking / Effort（思考与投入）**
- 新模型用 `thinking: {type: "adaptive"}`，**不要用 `budget_tokens`**（已废弃）
- 用 `output_config: {effort: "low"|"medium"|"high"|"xhigh"|"max"}` 控制思考深度
- `xhigh` 是编码和 agentic 场景的最佳设置

**Prompt Caching（提示缓存）**
- 前缀匹配。**渲染顺序：`tools` → `system` → `messages`**
- 稳定内容放前面，易变内容（时间戳、本次问题）放最后
- 用 `usage.cache_read_input_tokens` 验证命中。如果一直是 0，说明有静默失效因素

**Tool Use（工具调用）**
- 用 `strict: true` 保证参数严格匹配 JSON Schema
- `stop_reason` 是唯一事实来源：`tool_use` = 要调工具，`end_turn` = 结束，`pause_turn` = 长时 turn 暂停（原样传回）
- **工具失败也必须回传 `tool_result`**（设 `is_error: true`），否则 400

**Token 计数**
- 用官方的 `count_tokens` 接口，**不要用第三方估算库**

## 最后一段

回到第 0 部分那句话，现在你应该能读出它的第二层含义：

> **Agent 工程 2026 年的核心不是"让模型更聪明"，而是"构建一个能让不够聪明的模型安全失败的脚手架"。**

所有真正有效的技术——工具设计、上下文压缩、规格先行、测试门禁、独立验证、小步提交——都是在**降低单步失败的成本和检测延迟**，而不是在提升单步成功率。

**这对你的面试意味着**：你不需要证明"AI 让我变快了 X 倍"。你需要证明**你有一套让 AI 产出可控的方法，并且知道这套方法什么时候会失效**。
