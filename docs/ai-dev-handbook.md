# 第一部分 · 术语与概念

## 1.1 概念地图：五个层次

面试官问任何一个 AI 概念，你都可以先把它定位到某一层——**这本身就是加分项**，因为它说明你有结构而不是在背词条。

```
第 5 层  工作方式    SDD · Agentic Engineering · CLAUDE.md · 人类审批闸门
          ↑ 你在这个岗位上的主要战场
第 4 层  上下文工程  四支柱 · 四失效模式 · JIT 检索 · 压缩 · 子代理
          ↑ 决定了系统的成败
第 3 层  Agent      Workflow vs Agent · ReAct · 工具调用 · pⁿ 可靠性衰减
          ↑ 决定了能力的边界
第 2 层  检索       Embedding · Chunking · Reranking · RAG 评测
          ↑ 决定了喂什么信息
第 1 层  模型       无状态 · 上下文窗口 · 幻觉 · 采样 · 约束解码
          ↑ 决定了能力的下限与失效方式
```

**一句话总纲**：

> **LLM 是一个无状态、上下文有限、且会一本正经胡说八道的函数。**
> 上面五层，全都是在应对这一句话的某个分句。

## 1.2 你必须能讲清的十个概念

每个都给了「一句话定义 / 为什么重要 / 常见误解 / 面试怎么答」。**"面试怎么答"那栏才是重点**——它决定了你是"看过资料"还是"想过"。

### ① 上下文工程 ≠ 提示工程

- **定义**：提示工程关注**用词**，上下文工程关注**接线**（哪些信息、通过什么通道、什么时机送达模型）。前者是后者的子集。
- **为什么重要**：在生产级 agent 系统里，**prompt 通常只占上下文窗口的 5–10%**，其余全是它周围的信息架构。
- **常见误解**：以为"提示工程已死"。**没有**——它仍是基线技能，在 system prompt 和工具描述上不可或缺，只是**从属**了。
- **面试怎么答**：
  
  > "我区分这两件事。提示工程是措辞，上下文工程是接线。实际做起来，优化措辞的收益远小于补齐缺失的信息——出了问题我先查'我漏了什么'，而不是'我该怎么换个说法'。这次重建项目里最典型的一次：我第一版需求文档把'四种检测模式'当成了既定事实，因为它是我从上一版的口头描述里继承的；后来读代码才发现 UI 上只有三个模式页签。这不是措辞问题，是我把二手描述当成了上下文。"

### ② Context Rot（上下文腐化）

- **定义**：性能随输入变长而**持续下降，远在窗口填满之前就开始**。
- **为什么重要**：它是**架构性的，不是模型特定的**——根源是 Transformer 的 O(n²) 注意力，每个新 token 都在与所有已有 token 竞争。
- **推论**：**"我把整个代码库贴给你"是错误策略。**
- **面试怎么答**：
  
  > "上下文不是越多越好。黄金法则是'能找到最大化期望结果概率的最小高信号 token 集合'。所以正确做法是给轻量标识符——文件路径、命令、URL——让 agent 按需去取，而不是预加载。Claude Code 就是这个模式：即时拉取文件，而不是把代码库塞进窗口。"

### ③ 幻觉的真正成因

- **定义**：不是"数据库查不到"，而是 **next-token prediction 的必然副产品**——模型优化的是"听起来对"，不是"是真的"。
- **配套概念**：**语境不忠（context infidelity）**——检索到了正确信息，却未能把生成锚定于该信息。**这是比幻觉更隐蔽的失效**，因为你看不出它错了。
- **面试怎么答**：
  
  > "我不会试图'消除'幻觉，那是架构决定的。我做两件事：一是给它外部验证依据——测试、类型检查、真实的命令输出，质量来自外部机制而不是模型的自觉；二是把每条结论标上证据等级。这次重建里，我的一个分析 agent 汇报说项目里的 `.env` 含真实密钥并且已经提交进仓库。我没有直接写进文档，而是跑了两条命令——`git ls-files` 和 `git check-ignore`——结果它既没被追踪也被正确忽略。**子 agent 会自信地报出一个不存在的安全事故。**"

### ④ Workflow vs Agent ⭐

- **定义**：
  - **Workflow**：LLM 和工具按**预定义代码路径**编排，**控制权在你**
  - **Agent**：LLM 在循环中**自主**决定调用什么工具
- **为什么重要**：这是这个领域最需要分清的一组区分。**能用 workflow 解决的就不要用 agent**——因为 agent 的可靠性随步数指数衰减（pⁿ）。
- **面试怎么答**：
  
  > "我倾向于先问这个任务能不能做成 workflow。Agent 的吸引力是灵活，代价是每一步都有失败概率，n 步之后单步成功率要连乘。能确定路径的就写死路径，把不确定性限制在最小的范围内，只在真正需要自主决策的地方才放 agent。"

### ⑤ pⁿ 可靠性衰减

- **定义**：n 步任务的成功率 ≈ 单步成功率的 n 次方。单步 95%，20 步之后约 36%。
- **为什么重要**：**这一条解释了绝大多数 agent 项目的失败**，也是抵抗"agent 什么都能做"叙事的核心武器。
- **面试怎么答**：
  
  > "这是我判断一个 agent 方案可行性的第一把尺子。如果一个任务要 30 步、每步 97% 可靠，整体大概是 40%——这在生产里不可接受。所以要么减少步数，要么在中间插检查点做纠错，要么把它降级成 workflow。"

### ⑥ 约束解码 / 结构化输出

- **定义**：生成逐 token 进行，约束引擎插在 **logits 和采样器之间**，把会破坏 schema 的 token 的 logits 设为 **-∞**，softmax 后概率为 0 → **"非法输出的失效模式在字面上不可能发生"**。
- **必须分清的三件事**：

  | 机制 | 保证 | 不保证 |
  |---|---|---|
  | JSON mode | 输出是合法 JSON | **不强制 schema** |
  | Structured Outputs | 输出匹配给定 Schema | — |
  | Function calling | 参数符合函数签名 | — |

- **两个失效模式**：**过度约束**（enum 里没有正确答案 → 模型只能返回一个"错但合法"的值 → 要留"other"逃生舱）；**隧道视野**（从第一个 token 就强制 JSON 形状会损害推理质量 → 复杂任务先让它自然语言推理，再产出结构化输出）。
- **面试怎么答**：
  
  > "结构化输出是**采样层的约束，不是质量增强器**。它保证格式，不保证内容对。另外两个坑我会主动规避：枚举值留逃生舱，以及复杂推理不要一上来就套 JSON——会伤推理质量。"

### ⑦ 外部 Oracle：质量来自机制

- **定义**：Oracle = 外部验证依据（测试、类型检查、编译、真实命令输出）。**agent 自己说"我做完了"不构成验证。**
- **为什么重要**：一条验证纪律——
  
  > **"每个检查点的验证不能委派给产出它的 agent。"**
- **面试怎么答**：
  
  > "我的验收标准必须是**可执行的**，不是'看起来对'。比如'推理进行中健康检查的 p99 < 100ms'——这条能跑出来。如果一条需求没法变成可执行的检查，那它要么不够具体，要么根本没法验证。还有一个纪律：产出代码的 agent 不能自己验收自己的产出。"

### ⑧ 无状态性 → 缓存 → 成本杠杆

- **定义**：API 不记忆，每轮必须重发全部历史。
- **推论链**：无状态 → 重复前缀 → **Prompt Caching**（相同前缀命中缓存，读取价约 10%）→ **前缀改一个字节就全失效** → 所以 prompt 要**稳定前缀 + 可变后缀**排列。
- **keepalive**：暂停期间定时重发相同前缀，防止缓存 TTL 过期。
- **面试怎么答**：
  
  > "知道模型是无状态的，很多工程决策就顺下来了。比如我会把稳定不变的部分放前面——system prompt、项目约束、工具定义——把变化的部分放后面，这样缓存命中率高。反过来，如果我把时间戳放在最前面，整个缓存就废了。"

### ⑨ 理解债务（Comprehension Debt）

- **定义**：生成代码与人类理解之间的鸿沟。
- **为什么重要**：经验法则是"**跟不上就是在盖章**"——如果你无法解释 AI 写的每一行,你的审查就是形式。
- **面试怎么答**：
  
  > "我给自己定了一条：**我无法向别人解释的代码，不提交。**这也是我这次选择重写而不是继续改旧项目的原因之一——重写的过程逼我重新理解每一个设计决策。速度不是唯一指标，被释放的注意力才是。"

### ⑩ SDD 的三种形态（详见第二部分）

- **spec-first**：先写规格再写代码，**但规格完成后就可以丢**
- **spec-anchored**：规格作为**持续参考**保留，代码与规格共同演进
- **spec-as-source**：规格是**唯一真相来源**，代码是生成的产物
- **为什么重要**：**这三种经常被混为一谈**，而它们的成本、收益和失败模式完全不同。见 §2.2。

### SDD 相关（第二部分详述）

| 术语 | 一句话 |
|---|---|
| **Spec-driven development (SDD)** | 规格先行：**规格是真相来源，不是代码** |
| **spec-first** | 先写规格，写完可丢。最轻，收益也最小 |
| **spec-anchored** | 规格持续保留作参考，代码与规格共同演进。**多数团队的实际落点** |
| **spec-as-source** | 规格是唯一真相，代码是产物。**争议最大**，被比作 1990 年代 MDD |
| **constitution（章程）** | 项目的不可协商约束（技术标准、安全、性能、约定）。**最常被跳过、也最重要的一步** |
| **Markdown Monster** | 规格膨胀成"一半规格、一半实现计划、一半 QA 待办"的千行 markdown |
| **SpecFall** | 采用 SDD 但不改变协作方式 → 产出一堆**一出生就过期**的文档 |
| **Proportionality failure（比例失调）** | 用重流程处理小问题。经典案例：一个小 bug 变成 4 个用户故事 + 16 条验收标准 |
| **Silent spec-code drift（静默漂移）** | 规格是设计时快照，实现悄悄偏离而规格不更新。**linter 和 CI 看不见** |
| **Context blindness（语境盲区）** | 规格/计划/任务引用了不存在的 API、已死代码、错误的模块边界 |
| **False sense of control** | 规格变成"信心凭证"而非"治理凭证"——agent 常常并不完全遵循 |
| **Semantic diffusion（语义扩散）** | "SDD"逐渐被当成"详细提示词"的同义词，定义精度丧失 |
| **vertical slice（垂直切片）** | 按功能端到端切分，而非按层切分。SDD 推荐的实现粒度 |
| **drift gate（漂移闸门）** | 把规格-代码偏离变成**合并错误**而非靠自觉 |
| **MDD（模型驱动开发）** | 1990 年代的前身，因**抽象开销超过收益**而失败 |

### 工作方式相关

| 术语 | 一句话 |
|---|---|
| **Agentic Engineering** | 编排并监督 AI 写代码，**以审查人类 PR 的同等严格度**审查 |
| **Vibe Coding** | "描述并接受"。适合原型，不适合生产 |
| **人类审批闸门** | 在关键节点物理阻止 agent 继续，直到人批准 |

# 第二部分 · AI Agent SDD 详解

> 这是本篇的核心。**建议的阅读重点不是命令集（那是查手册的事），而是 §2.6 的失败模式**——那是这个领域目前最有信息量、也最少人讲清的部分。

## 2.1 SDD 要解决什么问题

SDD 不是凭空出现的，它针对 AI 编码的三个具体失败模式：

| 失败模式 | 表现 | SDD 的应对 |
|---|---|---|
| **无锚点** | agent 每次对话都从零猜你的意图，产出方向漂移 | 规格作为稳定的共同参照物 |
| **假设传播** | 一个早期错误假设被放大到许多特性上 | 在写代码**之前**澄清（`/clarify`） |
| **验证无依据** | "看起来对"就算完成，没有可执行的验收标准 | 验收标准必须可测量、可测试 |

**核心原则**（✅ 广泛共识）：

> **规格是真相来源，不是代码。代码是规格的产物。**
> **只写 WHAT 和 WHY，不写 HOW。实现细节属于 plan 阶段。**

第二条是 SDD 最容易做错的地方。技术栈、架构、目录结构**都是 HOW**，应该出现在 `plan.md` 而不是 `spec.md`。

## 2.2 ⭐ 三种 SDD 的谱系——最重要的一个区分

**Birgitta Böckeler（Thoughtworks）提出的分类**，在整个领域被广泛引用。**这一节如果只能记一件事，就记它。**

| | **spec-first** | **spec-anchored** | **spec-as-source** |
|---|---|---|---|
| **规格的地位** | 起点，写完可丢 | 持续参考，与代码**共同演进** | **唯一真相**，代码是生成的产物 |
| **代码的地位** | 主要产物 | 主要产物 | 派生物 |
| **成本** | 低 | 中 | 高 |
| **收益** | 澄清需求，防假设传播 | 防漂移，保留决策上下文 | 理论上杜绝漂移 |
| **主要风险** | 规格写完就过期 | 需要纪律维持同步 | **1990 年代 MDD 的重演** |
| **适用** | 小改动、一次性任务 | **多数团队的实际落点** | 极少场景 |

**为什么这个概念关键**：讨论中"SDD"经常被当成一个东西，但三种形态的成本、收益、失败模式**完全不同**。有人批评"SDD 是过度工程"，他批的通常是 spec-as-source；有人称赞它有效，他夸的通常是 spec-first 或 spec-anchored。**不区分这三种，这个讨论就没法进行。**

**关于 spec-as-source 的批评**（⚠️ 存在实质争议）：

- Böckeler 追溯到 1990 年代 **MDD（模型驱动开发）**的失败——**抽象开销超过收益**
- 规格作为单一真相来源是"**团队在实践中持续拒绝的脆弱单点**"
- LLM 引入了 MDD 没有的东西：**非确定性**。所以 spec-as-source 有"同时获得僵化和不可预测两者缺点"的风险

## 2.3 Spec Kit 的实际工作流

GitHub 的 **Spec Kit** 是 SDD 的参考实现。它有两类命令：**终端命令**（`specify init` / `specify check`）和 **AI 助手的斜杠命令**（`/speckit.*`）。

### 核心序列

| 顺序 | 命令 | 产出 | 说明 |
|---|---|---|---|
| 1 | `specify init` | 项目结构 | 生成 `.specify/memory/constitution.md`、`.specify/templates/`、`specs/` 等 |
| 2 | `/speckit.constitution` | `constitution.md` | 项目原则与不可协商约束。**跑一次即可** |
| 3 | `/speckit.specify` | `spec.md` | 从自然语言描述生成规格。**只写 what/why** |
| 4 | `/speckit.plan` | `plan.md` | 技术方案。**HOW 在这里** |
| 5 | `/speckit.tasks` | `tasks.md` | 按依赖与并行标记拆解的任务清单 |
| 6 | `/speckit.implement` | 源码 | 校验前置产物齐全后按序执行 |

### 可选的质检命令

| 命令 | 作用 | 位置 |
|---|---|---|
| `/speckit.clarify` | 识别歧义与未明确的边界情况，**最多问 5 个针对性问题**，答案折叠回 `spec.md` | 在 plan **之前** |
| `/speckit.checklist` | 生成质量清单——被描述为"**给你的需求写的单元测试**" | 任意 |
| `/speckit.analyze` | 跨产物一致性检查：plan 是否覆盖全部 spec 需求、tasks 是否覆盖 plan 全部要素、是否符合 constitution | tasks **之后**、implement **之前** |
| `/speckit.taskstoissues` | 把任务转成 GitHub issues | 可选 |
| `/speckit.converge` | 评估实现与产物的差距，追加剩余工作 | 收尾 |

### 两条推荐路径

- **短路径**（较小特性）：`specify → plan → tasks → implement → converge`
- **完整路径**（生产特性）：在上面基础上加 `constitution` 开头，`clarify` / `checklist` / `analyze` 作为质检闸门

### 几个容易记错的细节

- **`/speckit.specify` 是 `/speckit.plan` 之前唯一严格必需的命令**——constitution 不跑也能继续，但**强烈建议跑**
- `/specify` 的单位与**特性分支/目录是 1:1** 关系（如 `001-feature-name`）
- 当前激活的特性由 `.specify/feature.json` 跟踪，**不是从 git 分支读取的**（可用 `SPECIFY_FEATURE_DIRECTORY` 覆盖）
- 命令前缀因 agent 而异：Claude 用 `/speckit.*`，Codex 用 `$speckit-*`，Kimi 用 `/skill:speckit-*`
- 工作流是**迭代的**：需求变了就回到上游改产物，再重新生成下游——**而不是直接往代码里打补丁**

## 2.4 constitution：最常被跳过、也最重要的一步

Spec Kit 文档自己指出：**constitution（章程）阶段是团队最常遗漏、也最重要的**。

**它解决什么问题**：把仓库的**隐式约束**从审查者脑子里，搬到 **agent 首先阅读的文档**里。

典型内容包括：技术标准、安全要求、性能预期、编码约定、合规要求。它还会同步依赖模板（`plan-template.md`、`tasks-template.md`）。

**为什么它对你这个岗位格外重要**：`constitution.md` 和 `CLAUDE.md` / `AGENTS.md` 是**同一类东西**——都是"给 agent 的项目上下文"。而有一条反直觉但有实证的发现：

> 🔬 **LLM 生成的 `AGENTS.md` 略微降低了任务成功率，同时增加了 23% 的成本；人类编写的文件把成功率提升了约 4%。**

**写得好的有帮助，冗余的自动生成的有伤害。** 这直接指向一条原则：

> **`constitution.md` 必须是手写的，且必须是短的。** 每一行都在争夺 agent 的上下文预算（见 §1.2 ②）。

**编写规则**（沿用 §5.5 的结论）：

| 要 | 不要 |
|---|---|
| 精确的 setup/build/test 命令及参数 | 标准约定（PEP 8、Prettier 默认值） |
| 与默认不同的规则 | 配置文件里已有的命令 |
| 架构约束、明确边界 | 完整 API 文档 |
| 项目特有的坑 | 显而易见的建议（"写干净的代码"） |

**写命令，不写散文**：

> ✅ "Run `pnpm test`" 胜过 ❌ "we have a comprehensive testing strategy"

## 2.5 什么时候用、什么时候不用

**⚠️ 过度规格化是一种真实的失败模式**——"审查成本超过它所治理的改动"。对一次性原型、微小修复，完整流程通常**过重**。

决策清单：

| 情况 | 建议 |
|---|---|
| 一句话能说清的改动 | **跳过全部流程**，直接做 |
| 单文件、明确边界 | 直接做，但要说清验收标准 |
| 多文件、有架构影响 | **至少 `specify → plan`**，plan 必须人工审查 |
| 需求本身有歧义 | **先 `clarify`**，别急着 plan |
| 生产特性、多人协作 | 完整路径 + `analyze` 闸门 |
| 你在探索一个不了解的代码库 | **先 Explore，不要先写规格**——规格需要建立在真实代码之上 |

最后一条尤其重要，也是与 **Explore → Plan → Code → Commit** 这条核心工作流的接合点：**规格不是凭空写的，它建立在探索之上。**

## 2.6 ⚠️ SDD 的失败模式（最有价值的一节）

这一节是**面试时区分度最高的内容**。大多数人只会背工作流，而下面这些是"我知道它会在哪里坏掉"。

### ① 比例失调（Proportionality failure）

**一个 workflow 不适配所有问题规模。** 经典案例被反复引用：**把一个小 bug 变成"4 个用户故事和 16 条验收标准"。**

### ② Markdown Monster

有实践者记录：一个简单的 "Create User Profile" 故事膨胀成 **1,070 行 Markdown**，含 19 条验收标准、数据库字段、文件清单、测试清单——最终这份规格"**一半是规格，一半是实现计划，一半是 QA 待办**"。

两个附带的伤害：
- **规格里嵌入的代码片段会偏置后续实现它的模型**
- **审查 markdown 文件往往比审查代码更枯燥**——审查负担不降反升

### ③ SpecFall：一出生就过期的文档

有文章警告：采用 SDD 但**不改变利益相关方的协作方式**，风险是产出一个"**markdown monster**"，它"**一出生就在生成层层过期的文档**"。

### ④ 规格本身也会骗人 ⭐

这是最反直觉、也最关键的一条：

> **Explicit ≠ true. Structured ≠ correct.**

**语境盲区（context blindness）**：规格、计划、任务会引用**不存在的 API、已死的代码、错误的模块边界**。而因为中间产物会喂给后续步骤，**错误会被流程放大**。

**这一条直接质疑了 SDD 的前提**——"规格是真相来源"要求规格本身是真的，但规格是模型生成的，它会幻觉。**SDD 不能修正错误的规格**（Spec Kit 文档自己承认这一点）。

### ⑤ 静默漂移（Silent spec-code drift）

规格是**设计时快照**；实现会偏离（换了数据库引擎、多加了一个端点）而规格不更新。**这种偏离对 linter 和 CI 都是不可见的**——它是结构性失效，不是纪律问题。

**新兴对策**：把漂移变成**合并错误**（drift gate），而不是指望人记得同步。

### ⑥ 虚假的控制感

agent **经常并不完全遵循指令**。所以规格可能变成"**信心凭证（confidence artifact）而非治理凭证（governance artifact）**"——你以为你控制了，其实只是写了一堆文档。

### ⑦ 治理止于设计边界

有报道记录了一起事故：一个 agent **删除了线上生产环境**，造成 13 小时中断。关键不在于事故本身，而在于**团队已经审查了规格、批准了设计**——但**没有任何东西治理"对真实基础设施的执行"**。

> ⚠️【二手】此案例（涉及 Kiro / AWS 生产环境）本篇只从检索摘要中看到，**未核对一手来源**。面试引用前请自行验证。

**教训**：**规格审查不能替代执行期的技术约束**（权限、隔离环境、审批闸门）。

### ⑧ 历史回声：MDD

1990 年代 **MDD（模型驱动开发）**因为**抽象开销超过收益**而失败。批评者认为 spec-as-source 有重演的风险，且 LLM 额外带来了**非确定性**。

### ⑨ 语义扩散

"spec-driven development"**逐渐被当成"详细提示词"的同义词**，定义精度正在丧失。有人用德语词 *Verschlimmbesserung*（越改越糟）形容这种现象。

### ⑩ 隐性知识无法文档化 ⚠️

有实践者主张：很多好的工程判断**无法被干净地预先翻译成语言**。强行要求它，代价是把开发者从"**识别**"推向"**解释**"，而这会消耗能量、拖慢构建。

### ⭐ 一条重要的实证观察

> **更好的结果与"有经验的、具备良好整洁编码与架构实践的工程师"相关——SDD 是放大既有技能，而不是替代它。**

**这一条对你的面试定位是核心**：不要把"我会用 SDD"当卖点，要把"**我知道 SDD 放大的是什么**"当卖点。

## 2.7 SDD 与本项目（crop-guard-platform）

把这套落回到你正在做的事——**我已经在无意识地用其中一部分了**：

| SDD 概念 | 本项目的对应物 |
|---|---|
| `/speckit.specify` 的产物 | `docs/requirements.md`（WHAT/WHY，明确不含技术选型） |
| `/speckit.plan` 的产物 | 待做：`docs/adr/*.md`（HOW——技术选型与决策记录） |
| `constitution.md` | 待做：`CLAUDE.md`（项目的不可协商约束） |
| Explore 阶段 | 已完成：对 v1 的两份代码审计 |
| 垂直切片 | 待做：阶段 4 按功能端到端推进 |
| 可验证的验收标准 | 已部分做到：`requirements.md` 的 NFR 表 |
| 外部 Oracle | 待做：测试 + CI（v1 是零测试零 CI） |

**已经踩到、也印证了 §2.6 的坑**：

| 坑 | 本项目的实例 |
|---|---|
| **④ 规格本身会骗人** | 我把"四种检测模式"写进需求文档，因为它是从口头描述继承来的——**读代码才发现只有三个模式**。规则同样适用于规格：Explicit ≠ true |
| **⑤ 静默漂移** | v1 的 `data.yaml` 写着 `val: images/train`——**规格（yaml）与实现（只往 train 写）一致地错着**，谁也没发现 |
| **① 比例失调** | 我一开始从需求分析直接推到 5 个 ADR，被你叫停。对当前阶段来说那套流程过重 |
| **② Markdown Monster 的风险** | 需要警惕：`requirements.md` 已经 405 行，继续加内容前先问"这行会不会被读" |

## 2.8 面试怎么讲 SDD

**不要这样答**（背书式）：

> ❌ "SDD 是先写规格再写代码，Spec Kit 有 constitution、specify、plan、tasks、implement 五个命令。"

这是查手册就能得到的答案，不体现判断力。

**要这样答**（有判断）：

> ✅ "我把 SDD 分成三种形态看——spec-first、spec-anchored、spec-as-source，成本差一个量级。多数讨论把这三个混为一谈，所以'SDD 好用'和'SDD 过度工程'两个说法可以同时成立，它们说的其实是不同的东西。我自己接受的是 spec-anchored：规格作为持续参考，但代码是主要产物。
>
> 我知道它的失败模式。最反直觉的一条是**规格本身会骗人**——它也是模型生成的，会引用不存在的 API 和错误的模块边界，而且因为中间产物喂给后续步骤，错误会被流程放大。Spec Kit 官方自己承认它不能修正错误的规格。所以'规格是真相来源'这个前提，本身需要验证。
>
> 还有一条更硬：**治理不能止于设计边界**。有案例是团队审查了规格、批准了设计，但 agent 还是把生产环境删了——因为没有任何东西约束执行。规格审查不能替代权限、隔离环境和审批闸门。
>
> 最后，我看到的一个结论是 **SDD 放大既有技能，而不是替代它**。所以我不会把它当卖点，我会把它当作一个需要判断力才能用好的工具。"
