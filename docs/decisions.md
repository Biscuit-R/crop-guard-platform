## D1 · 推理并发模型

**选择** —— 线程池 + 并发上限（= CPU 核数）

**为什么** —— 归档四个检测端点都是 `async def` 却直接调同步推理，全库无一处 `run_in_executor`：单个请求推理期间**阻塞整个事件循环**，连健康检查和登录都排队。PyTorch / OpenCV 的算子跑在 C 扩展里会释放 GIL，所以线程池对推理真的有效。

**否决了** —— 进程池（每个进程一份模型副本，内存 ×N）· 独立推理服务（多一个部署单元 + IPC，单机 demo 过重）

**代价** —— 线程池容量必须 ≥ 并发上限，否则排队位置从信号量漂移到线程池，超时语义变模糊

**对应验收标准** —— `A2`：推理进行中健康检查 p99 < 100ms

## D2 · 对象存储

**选择** —— 保留 MinIO，**这次真的接线**

**为什么** —— **目标是将来实际部署到服务器**。本地磁盘把文件绑死在单机上：容器重建、换机器、多实例部署时文件会丢或对不上。对象存储让应用无状态化，这是能真正上服务器的前提。另外归档里有 `minio_utils.py`（175 行）但**零引用** —— 想了没做，这次要么真接线，要么砍干净，不能留一半。

**否决了** —— 本地磁盘（对单机 demo 够用，但把应用钉死在单机上）· 本地磁盘 + 薄接口（折中，仍不具备上服务器的条件）

**代价** —— 多一个容器、一套 SDK、一个故障点

## D3 · 执行模型

**选择** —— 全同步栈：端点写同步 `def`，SQLAlchemy 同步，推理走 D1 的专用线程池

**为什么** —— D1 选完之后，端点怎么写成了独立的选择题。同步栈只有一处范式，没有「哪层该 await」的困惑。

**否决了** —— 全异步栈（最现代，但推理本身仍是同步的 → 两套范式并存，容易搞混）· 混合（async 端点 + 同步 DB 包 `to_thread`，每个仓储方法都要手动线程隔离，容易漏一处）

**代价** —— 检测在等推理时会占着 FastAPI 的线程池（40 个里最多占 8 个）；**并发上限必须 ≤ 线程池容量**

## D4 · 依赖管理

**选择** —— uv

**为什么** —— 有 `uv.lock` 锁文件、能管 Python 版本、装依赖比 pip 快一个量级；Dockerfile 里也能用。

**否决了** —— `requirements.txt`（归档现状，无锁文件，"本机跑得起来、容器里装不出来"）· pip-tools（有锁文件，但工具链与生态已落后）

**代价** —— 国内需配 PyPI 镜像（清华 / 阿里），一行配置

## D5 · 静态类型

**选择** —— 只前端 TypeScript；后端维持 Pydantic 运行时校验 + SQLAlchemy 类型注解

**为什么** —— 归档前端那些问题（鉴权状态散落三处、日期格式化四份实现）根子都是**没有类型**。类型检查是最廉价的「可执行验证」——它在代码跑起来之前就失败。

**否决了** —— 两端都加 mypy（面试最硬，但 SQLAlchemy + mypy 有额外配置成本，且 Python 的动态性主要在 DB 层，收益不如 TS 明显）· 都不加（前端类型错误只能靠手测）

**代价** —— 前端开发略慢；**换来的是一部可执行的类型检查**

## D6 · 认证实现

**选择** —— PyJWT + 直接调 bcrypt 库（去掉 passlib 这一层）

**为什么** —— 归档留了两个具体的坑：`python-jose`，以及钉死的 `bcrypt>=4.0.0,<4.1.0`。**那个上界不是随便写的** —— `passlib` 1.7.4 与 `bcrypt` 4.1+ 不兼容，钉版本是绕过它的唯一办法。

**否决了** —— 沿用 python-jose + passlib（改动最小，但钉子得继续钉着，以后升 bcrypt 会撞同一面墙）· PyJWT + argon2（无 bcrypt 的 72 字节截断问题、抗 GPU 暴力破解更强，但多一个依赖）

**代价** —— 需要自己实现「哈希 / 校验」两个函数（passlib 原本代劳），约 10 行

## D7 · 模型接入形态（2026-10-01 新增）

**选择** —— 云 LLM（**DeepSeek**）做生成 + **本地** embedding 模型

**为什么** —— 两个环节的性质完全不同，所以不该用同一种方式：
- **embedding 是本地的**：它只在建索引时批量跑一次（500 个 chunk），之后每次查询只跑一次问题向量 —— 本地跑**零费用、延迟恒定、可离线建索引**。BGE-small-zh 约 100MB，CPU 足够。
- **生成走云 API**：本地 7B 模型 CPU 推理生成一段话要十几秒，云 API 是 1–2 秒。**面试现场演示时这个差距是决定性的。**
- **供应商选 DeepSeek**：价格最低、中文强，且是 **OpenAI 兼容接口** —— 换模型只改 `base_url` 与模型名，代码不动。

**否决了** —— 全部走云 API（建索引要逐条调 API，慢且花钱；断网即完全不可用）· 全部本地 Ollama（镜像大几 GB、生成慢、演示体验差）

**代价** —— 需要 API key 与少量费用；**生成环节依赖外网** → 断网时 RAG 的生成会失败。**这正好是降级语义的第三个场景**（见 `requirements.md` 的设计亮点）：检索成功但生成不可用时，降级为「只返回检索原文」，因为原文是可信的。

## D8 · 向量存储（2026-10-01 新增）

**选择** —— pgvector（PostgreSQL 扩展）

**为什么** —— 规模是 102 条语料切出的约 500 个 chunk。**pgvector 在这个量级毫无压力**，而且复用已有的 PG 容器 —— 不新增服务、不新增故障点、不新增备份对象。

**否决了** —— 独立向量库 Milvus / Qdrant / Chroma（功能更全，但对 500 个向量是**彻底的过度设计**，还多一个容器和一套运维）· 不用向量库（会失去语义检索 —— 而语义检索正是 RAG 相对关键词检索的核心价值）

**代价** —— postgres 镜像要换成 pgvector 版本；向量检索能力受 PG 限制，没有专用向量库的高级索引调优空间

## D9 · 应用框架（2026-10-01 新增 · 2026-10-02 修正理由）

**选择** —— **不用** LangChain / LlamaIndex，裸代码实现

**为什么** —— 三条，按分量排序：

1. **框架会把检索变成黑盒，而这恰好是本项目最强的卖点。** 项目原则是「每一行都要能 defend」。面试官问「top-k 为什么取 5」「相似度阈值怎么定的」「为什么用余弦不用内积」—— 如果代码里是 `vectorstore.similarity_search(q, k=5)`，你只能答「框架就是这么做的」。裸代码写出来，你能指着那 20 行说清每个数字的来源。
2. **降级语义不在框架的概念里。** 需求里那条「**检索置信度不足 → fail-closed 拒答**」是**业务判断**，LangChain 里没有对应东西，无论如何都要在它外面包一层自己写的判据。既然外层注定自己写，内层为 150 行的流程引入重依赖就不划算。
3. **流程本身只有四步**（embedding → 向量检索 → 拼 prompt → 生成），约 150 行。框架的收益主要是**统一接口**与**多后端切换** —— 而我们只用一种 embedding、一种向量库、一种 LLM，这两项收益归零。

**否决了** ——
- **LangChain**：能覆盖约 80% 的流程。**关键不是「它做不到」，是「不划算」。** 真实短板两条：① **版本动荡** —— `LLMChain` 在 0.3.0 中**已被移除**（不只是废弃），`AgentExecutor` 已进维护模式、官方要求 2026-12 前迁走，网上多数教程已过时。② **通用抽象与本场景错配** —— 语料是 Python dict 不是文件，`DocumentLoader` 价值归零；切块要按**字段**（`description` / `damage_symptoms` / `control_methods`）切而非按字符数，通用 `TextSplitter` 反而做不好。
- **LlamaIndex**：RAG 场景确实比 LangChain 更合适，但同样不必要 —— 理由同上第 3 条。

**代价** —— 没有现成的文档加载器与切分器，切分策略与检索逻辑要自己写（约 100 行）

> **面试用法**：这题的标准答法不是「我用了 X 框架」，而是「**我知道 X，我评估过，我没用，理由是……**」。⚠️ 注意华为 JD 第 2 条明写「熟悉主流大模型应用开发框架」—— 所以「不知道」是硬减分，**必须能说出 LangChain / LangGraph / LlamaIndex / Dify / 官方 SDK 的定位差异与选型逻辑**，再讲不用它的理由。见 `docs/notes.md` 对应条目。

## D10 · 拒答的判定语义（2026-10-02 新增）

**选择** —— 按检索置信度**分三档**：

| 档 | 条件 | 行为 |
|---|---|---|
| 高 | 高于**高阈值** | 正常作答 + 溯源到图鉴条目 |
| 中 | 落在**中间带** | **作答**，但显式标注「可能相关，请核对后再用药」 |
| 低 | 低于**低阈值** | fail-closed 拒答 |

**为什么** —— `requirements.md` 已定「检索置信度不足 → fail-closed」，但**没定「不足」怎么判**。三档是那条要求的落地：中间带既不该像高置信那样直接给方案（可能打错药），也不该像无关那样完全拒答（用户问的确实是这类病）。

**分档依据与 `requirements.md` 的设计亮点同构** —— 按**故障的代价**分级，不是二值开关。这是同一个原则在 RAG 模块上的第二次应用。

**否决了** ——
- **二元阈值**：0.84 与 0.86 被区别对待，但 0.84 的答案可能完全正确
- **`max(top-3) ≥ θ` 就作答**：与验收标准「10 条无关问题拒答率 = 100%」冲突，沾边的会漏进作答

**代价 / ⚠ 未定** —— **两个分界数字未定，且不得凭空填。** 讨论中曾出现 `0.85` / `0.65`，那是**示意值不是测量值**，写进代码即违规。必须用评测集在**同一 embedding 空间**下实测校准（阶段 4）。

**连带约束** —— 中间档是**作答**不是拒答，所以「拒答率 = 100%」要求那 10 条无关问题的相似度**全部低于低阈值**。**「多无关才算无关」这条线，同时定义了中间档的宽度。**

> **2026-10-03 更新**：评测集 B 节已拍板（路二）—— 4 条「农业相关但语料没有」的问题（B2）**承认落中间档是正确行为**，验收措辞改为「**6 条明显无关问题（B1）拒答率 = 100%**」。低阈值的约束从「10 条全拒」放松为「B1 的 6 条全拒」，中间档上边界仍由近缘难例约束。详见 `rag-eval-set.md` B 节。

**对应验收标准** —— `requirements.md` 知识问答行：`10 条无关问题拒答率 = 100%`、`30 条症状评测集 top-3 命中率 ≥ 80%`

## D11 · 语料切分粒度（2026-10-03 新增）

**选择** —— 每条切 **3 块字段组**，每块前缀虫名：

| 块 | 字段 | 服务哪个入口 |
|---|---|---|
| ① 认知块 | `description` + `morphology` + `host_plants` | 「这是什么虫」类问题 |
| ② 症状块 | `damage_symptoms` + `occurrence_period` | **入口②** 症状描述 → 虫害检索 |
| ③ 防治块 | `control_methods` | **入口①** 检测结果 → 治理方案 |

**为什么** —— 一条向量只装一种语义，检索精度才不被稀释：症状题命中②、治理题命中③，互不干扰。**前缀虫名**是关键细节 —— chunk 切出来会丢失「这段症状属于谁」的上下文，而溯源（答案挂到图鉴条目）靠 metadata 里的虫名回链。约 300 块，仍在 D8 估的 pgvector 无压力量级。

**前缀格式（2026-10-03 补充拍板）——【虫名·类型】，如【稻纵卷叶螟·症状】**。agent 曾推「纯虫名」（查询侧没有标签词，标签会稀释语义），但用户从**产品层**推翻：助手会用引导式提问（「有什么症状？什么特征？什么颜色？」）引导用户描述，查询侧**会真的出现标签词**——两侧对称后，标签词从噪声变成对齐信号；且带类型的块在语料扩充时自解释，新语料照格式就能对齐。教训：检索层的选择被产品行为翻转，**产品形态是检索设计的输入**。

**否决了** —— 整条一块（102 块，最简单，但形态+症状+防治混进一条向量，症状题与防治题互相干扰）· 两块（症状+描述合并 —— 症状块混入大量形态描述文字，检索区分度不如三块）

**代价** —— 向量数 ×3；切分逻辑比「按字符数」多约 20 行（但 D9 本来就定了按字段切，这部分是既有成本）

**对应验收标准** —— 评测集 s01–s30 症状题、n01–n10 无关题的命中/拒答都建立在这个切分上

## D12 · 入口①的生成语义（2026-10-03 新增）

**选择** —— 检测结果入口（YOLO `class_name` → 治理方案）**纯查表直出，不过 LLM**。

**为什么** —— ① 原文就是三段式标准答案，LLM 润色只引入幻觉风险、不增加信息；② **节约 token**（用户拍板理由）；③ 降级语义天然成立——原文可信，「断 LLM 降级返回原文」对入口①永远成立，因为它根本不依赖 LLM。入口①与②的性质由此彻底分离：**①是查表（精确 key），②是检索（模糊语义）**。

**否决了** —— 检测结果也过 LLM 生成个性化方案（费 token、引入幻觉面、且精确 key 的查询走向量/生成是用错工具——10-01 复盘里「入口选错」的教训）

**代价** —— 回答表述固定、不个性化。对治理方案这种**事实性内容**，固定是优点不是缺点
